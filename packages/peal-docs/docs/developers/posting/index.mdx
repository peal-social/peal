You can send posts from your own code through the [HTTP API](/developers), the SDKs, the command line or MCP. Each request below has a sample in every language, and the [API reference](/reference) lists every field.

## Before you start [#start]

Every endpoint here is under `/api/v1/posts`. You need an [API key](/guides/workspace#api-keys), which looks like `peal_…`. It acts in its own workspace, so no request names the workspace ([The workspace of a request](/developers/conventions#workspace)).

The samples read the key from `$PEAL_API_KEY`. The first sample builds the client, as [SDKs](/developers/sdks#credential) shows, and the others reuse it: `peal` in every language but Go, where it's `client`. The commands run in the workspace `peal` is signed in to ([Command line](/developers/cli)).

The ids are made up and the answers are shortened. A real answer always holds the whole post, as `GET …/posts/{postId}` returns it.

Each request needs these permissions:

| Request                        | What it does                              | Needs                                        |
| ------------------------------ | ----------------------------------------- | -------------------------------------------- |
| `POST …/posts/validate`        | Checks a post, and makes nothing          | `post:read`, `channel:read`                  |
| `POST …/posts`                 | Creates a post and sends it, now or later | `post:schedule`, `channel:read`              |
| `GET …/posts/{postId}/outcome` | Waits until a post has gone out           | `post:read`                                  |
| `POST …/posts/bulk`            | Creates and sends up to 50 posts          | `post:schedule`, `channel:read`              |
| `POST …/posts/import`          | Creates and sends the posts of a CSV file | `post:schedule`, `post:read`, `channel:read` |
| `GET …/posts`                  | Lists the workspace's posts, with filters | `post:read`, `channel:read`                  |

A post that shows media also needs `media:read`. An OAuth access token needs the scope `workspace:publish` for `create`, `bulk` and `import` ([What each permission allows](/developers/agents#scopes)).

<Callout type="warning" title="Peal can't take back a post once it's out">
  What `create`, `bulk` and `import` publish reaches the platforms' public, and
  you can't take it back from Peal once it's out. Until its time, you can still
  cancel or unschedule a post.
</Callout>

## Check a post without making it [#validate]

`POST …/posts/validate` takes the same body as `create`, or a draft's, which has no `when`. It writes nothing. The answer is 200 whether or not the post would go through, with `valid` and every reason it would be refused, all at once.

<CodeGroup>

```ts Node.js
import { PealClient } from "@peal-social/sdk";

const peal = new PealClient({ token: process.env.PEAL_API_KEY });

const check = await peal.posts.validate({
  channelIds: ["0190f3a0-0000-7000-8000-00000000c001"],
  content: {
    text: "Our spring catalogue is out. Read it at https://example.com/spring #spring",
    media: [],
    overrides: [],
  },
  when: { _tag: "at", at: "2026-11-16T08:00:00Z", timeZone: "Europe/Paris" },
});
```

The answer holds these fields:

| Field             | What it holds                                                                                                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `valid`           | True when nothing below refuses the post                                                                                                                                                           |
| `channels`        | One entry for each of the workspace's channels the post names, in the order you gave them                                                                                                          |
| `violations`      | What's wrong whatever the channel: no channel at all, or a text or options for a channel the post doesn't go to                                                                                    |
| `unknownChannels` | The channels it names that aren't the workspace's                                                                                                                                                  |
| `unknownMedia`    | The media it shows that aren't the workspace's, or aren't ready                                                                                                                                    |
| `schedule`        | `ok`, `inPast` (more than a minute ago) or `invalidTimeZone` (not an IANA zone). Null without `when`.                                                                                              |
| `planLimit`       | The limit of the workspace's plan the post would pass, as `PlanLimitReached` describes it. Null when the plan has room, on an instance that doesn't bill, or without `when`.                       |
| `awaitsApproval`  | Whether the post, sent as it is, would wait for an [approval](/guides/posts/review) before it's scheduled. It would still be made, with the status `awaitingApproval`. False without `when`.       |
| `duplicates`      | The channels that already get the same content from another post near its time, each with that post ([Duplicate posts](#duplicates)). Empty without `when`, or when the request allows duplicates. |

`awaitsApproval` refuses nothing. It tells you what the workspace asks of this caller.

Each entry of `channels` holds:

| Field                                       | What it holds                                                                                                                                                                                                                                                                                                           |
| ------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `text`                                      | The text the channel receives: its override there, or the post's own                                                                                                                                                                                                                                                    |
| `textCounts`                                | That text's length against each of the platform's limits, counted the way the platform counts. Bluesky has two, in graphemes and in bytes.                                                                                                                                                                              |
| `hashtags`, `mentions`, `links` and `media` | How many the post holds (`count`) and the most the platform takes (`maximum`, null when Peal knows no limit). `links` counts distinct links. `media` counts what the channel receives: its own when its override gives some ([Media of its own on a channel](#channel-media)), otherwise the post's.                    |
| `parts`                                     | The parts after the first of a [thread](/guides/posts#threads), in order, each with its `part` (its place, from 1), its `text` on the channel and the same counts. Empty for a single post. A platform that only takes single posts still lists them, and refuses them with `tooManyParts`.                             |
| `violations`                                | Every platform rule the post breaks, in any part (text, media formats, sizes, counts and durations, options), plus the account's own rules where its platform reports them. A violation about a later part names it by `part`. They read as in `PostContentInvalid` ([How refusals read](/developers/agents#refusals)). |

A post that would be refused also gets a 200, with `valid` false:

Without `when`, the request is checked as a draft, so the time, the plan's room and duplicates aren't checked.

<Callout type="info" title="A post that's valid now can still be refused later">
  That happens if a channel is disconnected or the plan's month fills up in the
  meantime.
</Callout>

## Publish now and wait for the outcome [#wait]

`POST …/posts` answers as soon as the post is made, while it's still publishing. Add `wait`, a number of seconds from 0 to 60, and a post that goes out now is answered once every channel has its result. The `Idempotency-Key` header lets you send the request again safely if the answer is lost ([Idempotency](/developers/conventions/idempotency#idempotency)).

<CodeGroup>

```ts Node.js
const post = await peal.posts.create({
  wait: "30",
  "idempotency-key": "5f0c2b7e-3d1a-4e58-9a6b-2c4d8e1f7a90",
  channelIds: [
    "0190f3a0-0000-7000-8000-00000000c001",
    "0190f3a0-0000-7000-8000-00000000c002",
  ],
  content: {
    text: "Our spring catalogue is out. Read it at https://example.com/spring",
    media: [],
    overrides: [],
  },
  when: { _tag: "now" },
});
```

The answer is 201 either way, because the post was made. What it holds depends on the wait:

- When every channel finishes in time, the post's `status` is `finished`, with its `outcome`. Each target is `published`, with its `permalink`, or `failed`, with its `failureReason`.
- When the time runs out first, you get the post as it stands, with some targets still `pending` or `publishing`. It goes on publishing.

A [thread](/guides/posts#threads) has its result on a channel once every part went out there, or one failed. Between two parts, its target stays `publishing`, and `parts.live` lists the parts that are out. If the thread waits longer between parts than `wait`, the time runs out first.

Without `wait`, it doesn't wait. These requests are also answered at once:

- A request for a draft, a cancelled post, or a post scheduled for later than the wait.
- A request that arrives while the server, or the workspace (10 at once), already has as many requests waiting as it allows. Ask again then.

Waiting changes nothing and holds nothing. The post publishes in its own job either way, and [webhooks](/developers/webhooks/events#events) still tell you how it went on each channel.

## Duplicate posts [#duplicates]

Peal refuses a post when another post of the workspace already sends the same content to one of its channels less than 23 hours from its time. The request answers 409 `DuplicatePost`, and nothing is made:

```json
{
  "_tag": "DuplicatePost",
  "duplicates": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "postId": "0190f3a0-0000-7000-8000-00000000b001"
    }
  ]
}
```

`duplicates` names each channel that already gets the content, with the earliest post that sends it there in that window. The check follows these rules:

| Rule             | Detail                                                                                                                                                                                                             |
| ---------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| The same content | The text the channel receives, and the same media in the same order.                                                                                                                                               |
| 23 hours         | The shortest day any time zone has, so a post that repeats every day at the same local time is never refused.                                                                                                      |
| What counts      | Posts that will go out or went out, including those waiting for an approval, since they go out once approved. Drafts, cancelled posts and a channel where the post failed don't count.                             |
| What is checked  | `create`, each item of `bulk`, each row of `import`, the MCP tools `create_post` and `create_posts`, and `peal post`. Scheduling an existing draft, moving a post and reposting where it failed are never refused. |
| When it's meant  | Send the request again with `allowDuplicate: true` on the post or the bulk item, or with `allow_duplicate` set to `true` on the CSV row.                                                                           |

`validate` reports the same thing beforehand, in `duplicates`.

<Callout type="info" title="This check is separate from idempotency keys">
  A key makes one request safe to send again. The duplicate refusal catches the
  same post requested twice.
</Callout>

## Your own id on a post [#external-id]

`externalId` is your own id for a post: the id of the record in your system it comes from, from 1 to 255 characters, compared exactly. Give it when you create the post (`create`, each item of `bulk`, the `external_id` column of an import, a draft). The answer carries it, and `GET …/posts?externalId=…` finds the post again.

An external id is unique in the workspace among posts that aren't cancelled. A second post with the same id is refused with 409 `PostExternalIdTaken`, and `postId` names the post that has it:

```json
{
  "_tag": "PostExternalIdTaken",
  "code": "post_external_id_taken",
  "postId": "0190f3a0-0000-7000-8000-00000000b001"
}
```

So a program that sends a creation again, an hour or a month later, never makes two posts. An `Idempotency-Key` is checked first: the same request under the same key answers the post it made. A post whose `status` is `cancelled` and a deleted draft free their id. A post cancelled while it was publishing ends `finished`, with the outcome `cancelled`, and keeps it: take it off with `setExternalId`. When one record makes several posts, give each its own id, such as `crm-record-42:linkedin`.

| Request             | What it does with the id                                                     |
| ------------------- | ---------------------------------------------------------------------------- |
| `create`, `bulk`    | Gives the new post the id, or refuses it when another post has it            |
| `validate`          | Answers `externalIdTakenBy`, the post that has the id already, or `null`     |
| `drafts.create`     | Gives the draft the id                                                       |
| `update` of a draft | Leaves the id as it is when `externalId` is left out, removes it with `null` |
| `setExternalId`     | Changes it on any post, whatever its status, or removes it with `null`       |

`PUT …/posts/{postId}/external-id` gives a post an id, whatever its status. Use it for posts made before your system kept ids, or to free an id. It says nothing to the platforms. It needs post:update.

## Media of its own on a channel [#channel-media]

A post's text on one channel, an entry of `content.overrides` or of a part's `overrides`, can also give that channel its own images and videos, in `media`. The channel then shows those instead of the post's:

| `media` on an override | What the channel shows                                                                  |
| ---------------------- | --------------------------------------------------------------------------------------- |
| Left out               | The post's images and videos. Peal only returns `media` on an override that gives some. |
| An empty list          | None.                                                                                   |
| A list                 | Those, in order, each with its alt text: 20 at most, ready media of the workspace.      |

An override always has a `text`, and it can't be empty. To give a channel its own media and nothing else, repeat the post's text there. That text then belongs to the channel, so when you change the post's text, change it there too (the web app does this for you).

```json
{
  "text": "Five pictures of the spring catalogue",
  "media": [
    {
      "mediaId": "0190f3a0-0000-7000-8000-00000000f001",
      "altText": "The cover"
    },
    { "mediaId": "0190f3a0-0000-7000-8000-00000000f002", "altText": "Page two" }
  ],
  "overrides": [
    {
      "channelId": "0190f3a0-0000-7000-8000-00000000c001",
      "text": "Five pictures of the spring catalogue",
      "media": [
        {
          "mediaId": "0190f3a0-0000-7000-8000-00000000f002",
          "altText": "Page two"
        }
      ]
    }
  ]
}
```

Media of its own changes a few other rules:

- Each channel is checked on the media it receives, by `validate` (its `media` count and its `violations`) and when the post is scheduled.
- The [duplicate check](#duplicates) compares what each channel receives.
- An approval covers every channel's media. Changing a channel's own media after the post was approved asks for an approval again.
- While a scheduled post shows a file on any channel, you can't delete that file from the library. A draft doesn't hold on to it, on any channel.

## Remove a channel from a scheduled post [#remove-target]

The request can be refused with these errors:

| Status | Code                     | When                                                                                                              |
| ------ | ------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| 409    | `last_target_left`       | The channel is the last one the post still goes out on. Cancel the post instead (`POST …/posts/{postId}/cancel`). |
| 409    | `post_status_conflict`   | The post is publishing or done, or it's a draft, whose channels you change with an update.                        |
| 409    | `target_status_conflict` | The channel was cancelled with its post.                                                                          |

A channel that was already taken off answers the post as it is, so it's safe to send the request again after a lost answer.

Taking a channel off counts as an edit of the post:

- Where your posts need an [approval](/guides/posts/review), the approval no longer covers it. The post is answered `awaitingApproval`, and waits for one again. A post already awaiting approval keeps its request, which now covers the post as it is.
- Webhooks receive a [`post.cancelled`](/developers/webhooks/events/posts#post-cancelled) that names that channel alone, with `scope` `target`.
- A post taken back to draft (`unschedule`, changes requested, or an approval after its time) keeps the channels it still had. The removed channel leaves with its target and its overrides in every part. If you name it again in `channelIds`, it gets a new, pending target.

It needs post:schedule, or, on a post awaiting approval, permission to ask for posts to go out. An OAuth client needs the scope `workspace:publish`.

## Polls and first comments [#polls]

`content.poll` adds a poll to the post's first part, whose text is the question. It has `choices` (2 to 4), `durationMinutes`, and `multipleChoice` (false when left out). Peal only returns it on a post that has one. Send `null`, or leave it out, for none.

A platform's capabilities describe its `poll`: how many choices, their `choiceLimit`, `durationMinutes` (`null` where the platform decides how long) and `multipleChoice`. Where they describe none, a post with a poll is refused with `pollNotSupported`. Each bound the poll breaks has its own violation: `pollChoiceCount`, `pollChoiceLength`, `pollDurationOutOfRange`, `pollMultipleChoice` or `pollWithMedia`. A repeated choice is `pollChoiceRepeated`, and Peal trims the spaces around each choice.

A first comment is the post's single part after its first (`content.followUps`), on platforms whose capabilities give `followUps` of kind `comment`. It's text only, within `commentTextLimits`. The capabilities only offer it where the server reads that platform's comments, so a channel connected before then is refused with `partsNeedReconnect`. Its capabilities say so beforehand, in `account.restrictions`. Some platforms add their own rules:

- On a LinkedIn page, `commentNeeds` says the page's administrator must have connected it.
- A YouTube video made for kids takes no comment (`commentsTurnedOff`).

A comment can fail after the post went live. The post is then `partiallyPublished`, and its target still counts as live for analytics, the inbox and ads. A repost sends the comment alone. `POST …/posts/{postId}/targets/{targetId}/leave-out-rest` publishes the target as a post without it (`partsLeftOut`). The [posts guide](/guides/posts#first-comment) explains how a lost answer is settled.
