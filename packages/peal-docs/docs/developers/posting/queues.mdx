You can let Peal pick a post's time from a queue's next free slot, make a post repeat, follow it up once it does well, or turn a web feed into posts. The samples build the client as [Posting through the API](/developers/posting#start) explains.

## Add a post to a queue [#queues]

A queue is a weekly timetable of slots in a time zone ([Queues](/guides/posts/queues#queues)). You manage queues with `GET` and `POST …/queues`, and `GET`, `PUT` and `DELETE …/queues/{queueId}`. Reading needs post:read, and changing needs post:update.

These requests put posts on a queue:

| Request                                                                                         | What it does                                                                                                                                         |
| ----------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| `when: { "_tag": "queue", "queueId": "…" }` on `send`, on each item of `bulk` and on `validate` | Puts a post on the queue's next free slot instead of a time. Leave `queueId` out for the workspace's default queue.                                  |
| `POST …/posts/{postId}/queue`, with `{ "queueId"?, "channelIds"? }`                             | Puts a draft on the next free slot, or moves a scheduled post, or one awaiting approval, there.                                                      |
| `GET …/queues/{queueId}/slots?count=…`                                                          | Previews the next slots, each with the post that holds it, and `nextFree`, where a post added now would go. It's advice only, since nothing is held. |
| `POST …/queues/{queueId}/reshuffle`                                                             | Moves the queue's waiting posts onto its slots as they are now ([below](#reshuffle)).                                                                |
| `GET …/posts/search?queueId=…`                                                                  | Lists the posts a queue placed. Each post carries the queue that placed it (`queueId`, null once that queue is deleted).                             |

### Send a post onto a queue [#queue-send]

This post names no channel, so it goes to the default queue's channels:

```ts Node.js
const post = await peal.posts.send({
  workspaceId,
  channelIds: [],
  content: { text: "An evergreen tip.", media: [], overrides: [] },
  when: { _tag: "queue" },
});
```

Peal decides the slot in the same transaction that saves the post, under the queue's lock. Posts sent together therefore take different slots, and a request sent again with its `Idempotency-Key` takes none.

A post that names no channel and no channel set goes to the queue's channels and channel set. Its answer's `warnings` name the queue's channels that were disconnected since (`queueChannelsDropped`).

`validate` answers `queueSlot`, the slot the post would take now, which is the time it checked everything else against. When the queue has no room, it answers `queueNoRoom`.

The [MCP tools](/developers/mcp/tools#tools) name the queue differently: `when: { "_tag": "queue", "queue": "…" }`, by its id or its name.

### Move a draft onto a queue [#queue-post]

`POST …/posts/{postId}/queue` puts a draft on the next free slot. It goes on `channelIds` if you give them, otherwise on its own channels, otherwise on the queue's channels and channel set, with the same `warnings` as a post sent onto the queue.

The post's own slot counts as free. So a post added again to its queue stays where it is, unless an earlier slot was freed since, which it then takes.

The request can be refused with these errors:

| Status | Code                 | When                                                                                                      |
| ------ | -------------------- | --------------------------------------------------------------------------------------------------------- |
| 409    | `queue_has_no_room`  | The queue has no slot, or every slot of the next 366 days is taken, with `reason` `noSlots` or `full`.    |
| 404    | `queue_not_found`    | The queue isn't the workspace's, or the workspace has no default queue.                                   |
| 402    | `plan_limit_reached` | The plan's room is counted in the slot's month. When that month is full, Peal never moves to a later one. |

### Move the waiting posts onto new slots [#reshuffle]

Saving a queue's slots moves no post. `POST …/queues/{queueId}/reshuffle`, with no body, moves the queue's waiting posts onto its slots as they are now ([Move the waiting posts onto new slots](/guides/posts/queues#reshuffle)). Waiting posts are those scheduled or awaiting approval, after now, including posts moved by hand, and they keep the order of their times. It needs post:schedule, or post:create where posts wait for an approval.

</CodeGroup>

Each move is a `reschedule`: the plan is counted in the new month, and `post.scheduled` is sent for a scheduled post. Approvals work differently:

- A scheduled post goes through the approval policy as the caller's post.
- A post awaiting approval keeps waiting at its new time, whoever calls. Its request still belongs to the requester, and `post.approval_requested` is sent with the new time.
- A post already on its slot isn't written.

The answer says what it did:

```json
{ "moved": 12, "unchanged": 3, "remaining": 0, "stoppedBy": null }
```

`remaining` counts the posts it hadn't placed when it stopped, and `stoppedBy` says why:

- `planLimit`: a month had no room.
- `full`: no slot is left within 366 days.
- `changed`: in the meantime, the queue was saved, or a post was added to it on a slot not yet reached.

Call it again to carry on. A second call right after the first moves nothing. A queue with no slot answers 409 `queue_has_no_room` (`noSlots`).

## Repeat a post [#recycling]

`POST …/recycling` makes a post that's scheduled, publishing or out repeat ([how it works](/guides/posts/queues#recycling)). It answers 201 with the rule, whose `coming` lists its next three posts and the variant each one uses.

The body takes these fields:

| Field      | What it holds                                                                               |
| ---------- | ------------------------------------------------------------------------------------------- |
| `postId`   | The post to repeat                                                                          |
| `every`    | `{ "count", "unit" }`: `unit` is `days` (1 to 365), `weeks` (1 to 52) or `months` (1 to 12) |
| `count`    | Optional. The number of posts in all, the source included (2 to 100)                        |
| `until`    | Optional. The last day, as `YYYY-MM-DD` in the source's time zone                           |
| `variants` | Optional. Each variant is `{ "text", "overrides"? }`, 10 at most                            |
| `queueId`  | Optional                                                                                    |

This rule posts six times in all, every two weeks, with one variant:

<CodeGroup>

### Manage a rule [#recycling-manage]

Once a rule exists, these requests read and change it:

| Request                                                    | What it does                                                                                                                             |
| ---------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| `GET …/recycling`                                          | Lists the rules, oldest first (`status`, `limit`, `cursor`)                                                                              |
| `GET …/recycling/{ruleId}`                                 | Reads one                                                                                                                                |
| `PATCH …/recycling/{ruleId}`                               | Changes its `count` or `until` (null removes it) or its `variants` (an empty array removes them), or pauses it (`paused`)                |
| `POST …/recycling/{ruleId}/resume`, with `{ "variants"? }` | Starts a paused rule again, or one that ended for `planLimit`, `contentRejected`, `noChannels`, `queueFull` or `sourceWithdrawn` (below) |
| `DELETE …/recycling/{ruleId}`                              | Stops it. The posts it made stay.                                                                                                        |
| `GET …/posts/search?recyclingId=…`                         | Lists the posts a rule made. Each carries `recyclingId` and `occurrence` (its place, the source being 1).                                |

A rule ends with `sourceWithdrawn` when its post was cancelled or taken back to draft. You can resume it once the post is scheduled again. Until then, resuming answers 409 `post_not_recyclable`, and it does the same while another rule repeats the post. Past 100 rules going on, it answers 409 `too_many_recycling_rules`.

### Who can do what [#recycling-permissions]

Rules follow these permissions:

- Starting, changing, pausing, resuming and stopping a rule needs post:schedule (or post:create, for starting, where posts wait for an approval). Staff acting as a member can't. Reading needs post:read.
- Changing, pausing, resuming or stopping a rule needs post:schedule, or being the person who started it, acting the same way: in the web app, through the same application or with the same key.
- Each post the rule makes acts as the rule's starter as they are at that moment. A key's rule stops once the key is revoked.

The requests can be refused with these errors:

| Status | Code                         | When                                                                                                                                                                                                                                |
| ------ | ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 409    | `post_not_recyclable`        | The post can't repeat. `reason`: `draft`, `awaitingApproval`, `cancelled`, `repeating` (another rule repeats it), `occurrence` (a rule made it) or `noChannels`.                                                                    |
| 422    | `recycling_variants_invalid` | Variants break the source's channels' rules, each by its place from 1 with its violations. An empty variant text that leaves a channel showing [media of its own](/developers/posting#channel-media) with no text is `empty` there. |
| 422    | `recycling_ends_too_soon`    | The ending leaves no post to make.                                                                                                                                                                                                  |
| 409    | `too_many_recycling_rules`   | 100 rules are already going on.                                                                                                                                                                                                     |
| 409    | `recycling_rule_ended`       | A change to a rule that has ended.                                                                                                                                                                                                  |

```bash curl
  -d '{"postId": "0190f3a0-0000-7000-8000-00000000b001", "likes": 50, "comment": "Thank you all for reading!", "repost": true}'
```

</CodeGroup>

The answer is the rule. It holds these fields:

- `approval`: `notNeeded`, `pending` or `approved`.
- `channels`: what each channel can carry, kind by kind. Each is `available`, `notAsked`, or the reason it can't, such as `notAllowed` on LinkedIn, or `reconnect` on a Bluesky channel connected before Peal asked to repost there.
- `followUps`: the latest follow-ups, each with its `status` and its `reason`.

A follow-up's `status` is `armed` until `until`, `waiting` until `until` for its channel to be connected again, `sending`, `sent` (with `platformPostId` and `permalink`), `failed`, `unconfirmed`, `expired` or `cancelled`.

`FollowUpNotPossible` (422) refuses a rule no channel can carry, or whose comment is too long for a channel that could, with the same `channels`. On a post with nothing left to publish, it also refuses a rule that would arm nothing (`alreadyFollowedUp`, `windowPassed`).

These requests manage a rule:

| Request                              | What it does                                                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------- |
| `PATCH …/follow-ups/{ruleId}`        | Changes `likes`, `comment` (null removes it) and `repost`, or pauses the rule (`paused`) |
| `POST …/follow-ups/{ruleId}/approve` | Approves it. A member has to do it in person.                                            |
| `DELETE …/follow-ups/{ruleId}`       | Stops it                                                                                 |
| `GET …/follow-ups?postId=…`          | Lists a post's rules                                                                     |

## Post from a feed [#feeds]

`POST …/feeds` follows a web feed ([how it works](/guides/posts/queues#feeds)). Peal reads it once, records every item it holds at that moment as seen, and never makes posts from them. It answers 201 with the feed and `seen`, the number of items it recorded.

The body takes these fields:

| Field                        | What it holds                                                                                                                                                     |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url`                        | The feed's address                                                                                                                                                |
| `channelIds`, `channelSetId` | Optional                                                                                                                                                          |
| `mode`                       | Optional. `draft` (the default) or `queue` (on `queueId`, or the workspace's default queue)                                                                       |
| `queueId`                    | Optional                                                                                                                                                          |
| `template`                   | Optional. It takes `{title}`, `{link}` and `{summary}`, 1000 characters at most.                                                                                  |
| `attachPicture`              | Imports each item's picture into the media library for its post (whoever adds the feed needs media:upload). An item's `pictureSkipped` says why one was left out. |

### Manage a feed [#feeds-manage]

These requests read and change a feed:

| Request                      | What it does                                                                                                                                                                                             |
| ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET …/feeds`                | Lists the feeds, oldest first (`limit`, `cursor`)                                                                                                                                                        |
| `GET …/feeds/{feedId}`       | Reads one: its `status`, `lastCheckedAt`, `nextCheckAt`, `failingSince` and `lastFailure`                                                                                                                |
| `PATCH …/feeds/{feedId}`     | Changes what it names (a new `url` is read at once, as when a feed is added), pauses it (`"status": "paused"`) or starts it again (`"active"`, read at once, and what it holds is never made into posts) |
| `DELETE …/feeds/{feedId}`    | Stops following it. Its drafts and posts stay.                                                                                                                                                           |
| `GET …/feeds/{feedId}/items` | Lists its 50 newest items with what became of each (`made`, `heldBack` with its `reason`, `skipped`, `claimed`, `abandoned`) and the post made, never their text                                         |

Reading needs post:read. Everything else needs post:create, plus post:schedule for a feed that is or becomes `queue`, so an application allowed only drafts can't make one. Someone without post:schedule can only change a feed they added, acting the way they added it.

The requests can be refused with these errors:

| Status | Code                    | When                                                                                                                                                      |
| ------ | ----------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 422    | `feed_address_refused`  | The address isn't a public HTTPS one (`reason`).                                                                                                          |
| 422    | `feed_unreadable`       | The address isn't a feed (`notAFeed`, `tooLarge`, `unreachable`).                                                                                         |
| 422    | `feed_template_invalid` | The template names another placeholder.                                                                                                                   |
| 409    | `too_many_feeds`        | The workspace already has 10 feeds.                                                                                                                       |
| 429    | `feed_reads_limited`    | Adding, moving, resuming and previewing read 30 addresses per workspace per hour. Past that, this error comes with `retryAfterSeconds` and `Retry-After`. |
