You can find the posts that failed last week, everything still scheduled on one channel, or the posts a key created. The samples build the client as [Posting through the API](/developers/posting#start) explains.

## Filter the posts [#search]

`GET …/posts` lists the workspace's posts, whatever their state, a page at a time. A page holds 20 posts unless `limit` says otherwise, and 100 at most. When you give several filters, a post must match all of them. The [MCP tool](/developers/mcp/tools#tools) `list_posts` takes the same filters, and `peal posts list` lists the same posts ([Command line](/developers/cli/posts#posts)).

The request takes these parameters:

| Parameter      | What it keeps                                                                                                                                                                                                       |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`       | `draft`, `awaitingApproval` (waiting for an [approval](/guides/posts/review), with its time kept), `scheduled`, `publishing`, `finished` or `cancelled`                                                             |
| `outcome`      | How a finished post ended: `published`, `partiallyPublished`, `unconfirmed`, `failed` or `cancelled`                                                                                                                |
| `channelId`    | Posts with a target on that channel                                                                                                                                                                                 |
| `platform`     | Posts with a target on a connected channel of that platform                                                                                                                                                         |
| `tagId`        | Posts filed under that tag                                                                                                                                                                                          |
| `queueId`      | Posts that queue placed ([Queues](/developers/posting/queues#queues))                                                                                                                                               |
| `recyclingId`  | Posts that recycling rule made ([Repeat a post](/developers/posting/queues#recycling))                                                                                                                              |
| `removed`      | `true`: posts Peal deleted from at least one channel's platform; `false`: posts deleted from none ([Unpublish a post](/developers/posting/published#unpublish))                                                     |
| `from`, `to`   | Posts scheduled from `from` (included) to `to` (excluded). Either one leaves out posts without a time.                                                                                                              |
| `createdVia`   | `web`, `apiKey` or `application`                                                                                                                                                                                    |
| `authorId`     | Posts that user created                                                                                                                                                                                             |
| `externalId`   | The post with that id of yours, compared exactly, and the cancelled ones that had it ([Your own id on a post](/developers/posting#external-id))                                                                     |
| `updatedSince` | Posts whose `updatedAt` is at or after that instant                                                                                                                                                                 |
| `sort`         | `createdDesc` (the default) or `createdAsc`, by creation; `scheduledDesc` or `scheduledAsc`, by scheduled instant, which list only posts with a time; `updatedDesc` or `updatedAsc`, by when each post last changed |
| `limit`        | How many posts a page holds, from 1 to 100                                                                                                                                                                          |
| `cursor`       | The `nextCursor` of the previous page                                                                                                                                                                               |

This request lists the failed Bluesky posts, the latest scheduled first:

<CodeGroup>

```ts Node.js
import { PealClient } from "@peal-social/sdk";

const peal = new PealClient({ token: process.env.PEAL_API_KEY });

  status: "finished",
  outcome: "failed",
  platform: "bluesky",
  sort: "scheduledDesc",
  limit: "50",
});
```

## Read the next page [#next-page]

Pass `nextCursor` as `cursor`, with the same filters and sort. It's null on the last page.

A cursor marks where its page ended, so posts created, moved or deleted in the meantime never make a page repeat a post or skip one. A cursor from another sort, or one no page returned, answers 400.

## Keep another system in step [#sync]

Every post has `createdAt`, read from its id, and `updatedAt`, when what its answer shows last changed. That covers the post's content, time, status, outcome, tags, queue and external id, and its targets: a channel that publishes, fails, is edited or unpublished moves its post. Each change moves `updatedAt` forward, never back.

To copy the workspace's posts into another system and keep it current, walk the list by change:

<Steps>
  <Step title="Read every page from an instant">
    List with `sort=updatedAsc` and `updatedSince` set to where the last run
    stopped (leave it out the first time), and follow `nextCursor` until it is
    null.
  </Step>
  <Step title="Save each post">
    Write each post as it comes, by its `id`. A post that changed during the
    walk comes again at its end: keep the copy you read last.
  </Step>
  <Step title="Remember where you stopped">
    Keep the last post's `updatedAt`, and give it as `updatedSince` next time.
    That instant is included, so its post comes once more, which changes
    nothing.
  </Step>
</Steps>

`updatedAsc` never lists a post that changed in the last 5 seconds. A change that has not finished saving can't land behind a cursor you already hold, so a walk may show a post twice but never misses one. The other orders hold nothing back.

<Callout type="info" title="What a walk doesn't tell">
  A deleted draft is in no list any more, so a walk never shows it. After the
  upgrade that added `updatedAt`, every existing post has the same instant, so
  the first walk reads them all once.
</Callout>

<Callout type="info" title="A calendar can read a whole range in one request">
  `GET …/posts/calendar?from=…&to=…` lists the posts scheduled between two
  instants, at most 62 days apart, by scheduled instant, in one answer. Drafts
  aren't included.
</Callout>
