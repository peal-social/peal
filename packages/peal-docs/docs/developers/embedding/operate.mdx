Once a customer has a workspace and a connected channel ([Embedding Peal](/developers/embedding)), your backend runs it with your partner key.

## Post for them [#post]

In a customer's workspace, your key calls the same endpoints as any other client: [media](/guides/media), [posts](/guides/posts) and [analytics](/guides/engage/analytics). A partner key belongs to no workspace, so each request names the customer's in the `Peal-Workspace` header. In the SDKs, that's the client's `workspace` option: make one client per customer workspace. The partner API's own calls in the sections below (`partner`, `partner.customerUsage`) name no workspace, so they go through a client made without one: `peal` in these samples, `client` in Go.

This publishes a post in one call, at a given instant:

<CodeGroup>

```ts Node.js
import { PealClient } from "peal-sdk";

// The partner API's client, which names no workspace.
const peal = new PealClient({
  token: process.env.PEAL_PARTNER_KEY,
  baseUrl: "https://api.example.com",
});

// Your customer's workspace, and one of its channels.
const workspaceId = "7b1f6c1e-2d4a-4f0b-9c3e-5a8d2e6f1b90";
const channelId = "019a6f40-11aa-7c3d-8e21-9f0b6a5d4c33";

// A client that acts in that workspace: a partner key belongs to none.
const customer = new PealClient({
  token: process.env.PEAL_PARTNER_KEY,
  baseUrl: "https://api.example.com",
  workspace: workspaceId,
});

const post = await customer.posts.create({
  "idempotency-key": "campaign-881-cus_42",
  channelIds: [channelId],
  content: { text: "Fresh bread at 7.", media: [], overrides: [] },
  when: { _tag: "at", at: "2026-11-12T06:00:00Z", timeZone: "Europe/Paris" },
});
```

To publish at once, send `when` as `{ "_tag": "now" }` instead. Peal checks the post against every channel's platform before it takes it, and answers every violation at once ([How refusals read](/developers/agents#refusals)).

## Hear what happened [#webhooks]

Add one endpoint to your home workspace with `scope: "partner"`. It hears the events of every workspace your partner account owns, and your home workspace's own.

A partner key doesn't act in your home workspace. So create the endpoint in the web app, signed in, under **Settings**, then **Webhooks**, or with an [API key](/guides/workspace#api-keys) of the home workspace that holds `webhook:manage`:

<CodeGroup>

The answer holds the endpoint's signing secret, shown this once. An endpoint with `scope: "partner"` in a workspace without a partner account answers 404 `PartnerNotFound`.

Every payload names its workspace twice. `data.workspaceId` is Peal's id, and `workspaceExternalId` is yours, as it was when the event happened (null when you gave none):

```json
{
  "id": "019a6f40-2f6b-7a1c-9d2e-5b4c3a2f1e07",
  "type": "channel.connected",
  "version": 1,
  "timestamp": "2026-11-10T09:14:02.000Z",
  "workspaceExternalId": "cus_42",
  "data": {
    "workspaceId": "7b1f6c1e-2d4a-4f0b-9c3e-5a8d2e6f1b90",
    "channelId": "019a6f40-11aa-7c3d-8e21-9f0b6a5d4c33",
    "platform": "linkedin",
    "reconnected": false
  }
}
```

[Webhooks](/developers/webhooks) explains how deliveries are signed, verified, retried and logged. An endpoint in one customer's workspace, with the default scope, hears that workspace alone.

A few events and settings help most when you embed Peal:

- [`post.finished`](/developers/webhooks/events/posts#post-finished) comes once every channel of a post has its result, with each one's. Subscribe to it to mark a customer's post done in your product, once.
- [`channel.expiring`](/developers/webhooks/events/channels#channel-expiring) warns you, a week ahead at most, that a channel's sign-in can't be renewed. Send your customer a [connect link](/developers/embedding#reconnect) before it lapses.
- `headers` gives the endpoint [headers of its own](/developers/webhooks#headers), for a receiver behind a gateway that wants a token. Their values are write-only.

### Keep staging apart with a workspace filter [#webhooks-staging]

Give each environment a partner endpoint of its own, and list in `workspaceIds` (200 at most) the workspaces it should hear. Your staging endpoint then hears your test customers, while your production endpoint, with no list, hears every workspace. Your home workspace is heard only when it's listed.

As you add test customers, change the list with `PATCH …/webhooks/{endpointId}`.

Your home workspace's [log across endpoints](/developers/webhooks/delivery#log) holds the deliveries of every endpoint, each with its workspace and your id for it. You can send the failed ones again together from there.

The answer has a section per area for each workspace:

```json
{
  "account": { "overPlan": false },
  "next": "eyJjcmVhdGVkQXQiOjE3OTQzMDEyMDMwMDAsImlkIjoiN2IxZiJ9",
  "total": 412,

        "scheduledNext7Days": 4,

        "mayApprove": true
      },
      "inbox": { "unanswered": 2 }
    }
  ]

```

Each figure counts one thing, and the key needs a permission to read it:

| Figure                       | What it counts                                                                                                | Opened by         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------- | ----------------- |
| `channels.connected`         | The channels connected in the workspace                                                                       | `channel:read`    |
| `channels.toReconnect`       | Those to [reconnect](/developers/embedding#reconnect), as `channel.reconnect_needed` told                     | `channel:read`    |
| `channels.off`               | Those turned off, on which nothing goes out                                                                   | `channel:read`    |
| `posts.scheduledNext7Days`   | Posts going out in the next 7 days                                                                            | `post:read`       |
| `posts.awaitingApproval`     | Posts waiting for an [approval](/guides/posts/review); `mayApprove` says whether the key holds `post:approve` | `post:read`       |
| `posts.failedLast7Days`      | Posts that finished in the last 7 days with a channel that failed, as `post.failed` told                      | `post:read`       |
| `posts.unconfirmedLast7Days` | Posts of the last 7 days with a channel that may be live and must be checked, as `post.unconfirmed` told      | `post:read`       |
| `inbox.unanswered`           | Threads of the [inbox](/guides/engage/inbox) with a comment waiting for an answer                             | `engagement:read` |

A section is `null` where the key wasn't given the permission that reads it. That's different from nothing to look at: a workspace with nothing going on answers zeros. The key needs the scope `workspaces:read`.

`account.overPlan` comes on the first page only. It says whether your workspaces, which share one plan and one channel count, hold more channels than the plan allows. If they do, they schedule and publish nothing until some channels are removed ([Plans and limits](#limits)). Before your first customer, it's your home workspace's own standing. It's `null` on a server that doesn't bill.

### Page through every customer [#health-pages]

Pages follow the list of your workspaces: newest first, 50 a page unless `limit` says otherwise (100 at most), with `next` passed as `before`. Your home workspace isn't listed, since it isn't a customer.

Nothing filters the list down to the workspaces that need attention, so page through all of it. For 1,000 customers that's 10 to 20 calls, well within the [rate limit](/developers/conventions/rate-limits#rate-limits).

### As a person in your home workspace [#health-home]

Your home workspace's owners and admins can read the same overview at `GET /api/v1/partner/account/overview` (`partner:read`), in **Settings**, then **Partner**, and with `peal partner overview` ([command line](/developers/cli/workspace#partner)).

They see each section where they hold its permission in the home workspace. Staff acting as one of them read no inbox. `mayApprove` is always false for them, because they're members of no customer's workspace.

The answer holds two things. `channel` is the channel in the workspace it went to, under a new id, so keep that one. `postsLeft` counts the posts of the workspace it left that still had the channel to go out on. They fail there for it.

The move needs the scope `workspaces:write`, and the key's permissions `channel:connect` and `channel:disconnect`.

### Send a move again safely [#move-again]

With an `Idempotency-Key` header, a request sent again within 24 hours (after a timeout, say) answers the channel the first one moved, as it now stands, and moves nothing. The same key with another request answers 409 `IdempotencyKeyReused`.

Without one, a request sent again after a move answers 404 `ChannelNotFound`, because the old id is gone. Look for the account in the workspace it was moved to.

The workspace it left sends [`channel.disconnected`](/developers/webhooks/events/channels#channel-disconnected), and the other sends [`channel.connected`](/developers/webhooks/events/channels#channel-connected). Both workspaces' [activity logs](/guides/workspace#activity) keep the move.

### What moves with the channel [#move-what]

The account goes, and most of what the old workspace built around it stays:

| What                                | After the move                                                                                                                                                            |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The account, its tokens, its status | In the workspace it went to. A channel turned off stays off, and one to reconnect stays to reconnect.                                                                     |
| Its name in the workspace           | Left behind. The other workspace gives it its own.                                                                                                                        |
| Posts, drafts and scheduled posts   | Stay in the workspace they were made in. Those still to go out on the channel fail there, as a disconnected channel's do (`postsLeft` counts them), so change them first. |
| Queues, channel sets, recycling     | Stay, and skip the channel as a disconnected one.                                                                                                                         |
| Analytics                           | The numbers stay in the workspace it left, kept a week as a disconnected channel's are, and come back if it returns within that week. The other workspace starts afresh.  |
| Inbox threads and direct messages   | End in the workspace it left, as a disconnected channel's do. The other workspace reads the account's comments and messages afresh.                                       |
| Plan and usage                      | Your workspaces share one plan, so the move counts no extra channel, and no plan limit refuses it.                                                                        |

### When a move is refused [#move-errors]

A move can answer these errors:

| Answer                     | Why                                                                                                                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 404 `WorkspaceNotFound`    | Either workspace isn't one your partner account owns. That includes your home workspace and anyone else's.                                                                                                                                                                                                          |
| 404 `ChannelNotFound`      | The workspace has no channel with this id                                                                                                                                                                                                                                                                           |
| 409 `ChannelAccountTaken`  | The workspace it goes to already has a channel of the same account (`channelId`), or is the one it's in                                                                                                                                                                                                             |
| 409 `IdempotencyKeyReused` | The `Idempotency-Key` was used for another request in the last 24 hours                                                                                                                                                                                                                                             |
| 409 `WorkspaceBusy`        | A call through the channel is in flight for the workspace it leaves (a post, a change of a live post, a follow-up, a reply, an answer to a review, a direct message), or another request holds either workspace for more than 5 seconds. Send it again a moment later. Reads through the channel aren't waited for. |

<Callout type="warning" title="Deleting a workspace can't be undone">
  It erases everything the workspace holds, for good: its channels and their

  included, which then go out nowhere, its media and their files, its analytics,
  its webhook endpoints and its connect links.
</Callout>

While one of its posts is being published, the deletion answers 409 `WorkspaceBusy`. Send it again a moment later. Afterwards, its external id is free again.

Your partner account closes, and your home workspace can be deleted, only once the account owns no workspace. Until then, both answer 409 `PartnerOwnsWorkspaces`.

## Plans and limits [#limits]

On an instance that bills, the workspaces your partner account owns have no subscription of their own. Together with your home workspace, they make up your partner account's billing account. One subscription, on the home workspace, pays for all of it, on one invoice a month.

Each limit is counted like this:

| Limit                                                | How it's counted                                                                                                                                                                                                                                                                                                                                                                                      |
| ---------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Channels                                             | Together. The free accounts and the ladder of [per-account pricing](/guides/workspace/billing#pricing) count the channels of your home workspace and of every workspace you own as one. On the free tier, connecting one more than it includes answers 402 `PlanLimitReached`, and a hosted page says no more accounts can be connected for now. With a payment method, each is billed by the ladder. |
| Usage meters                                         | Together. Each [meter](/guides/workspace/billing#meters)'s monthly allowance covers all your workspaces.                                                                                                                                                                                                                                                                                              |
| Media stored, the writing assistant's requests a day | Together too. They cover your home workspace and every workspace you own as one payer's, so a customer that spends the day's requests leaves none for the others until midnight UTC. Images from a customer's own image provider, and requests to its own text provider, count against none of them.                                                                                                  |
| Posts scheduled in a month                           | Unlimited. On a plan priced by channels that limits them, each workspace gets what the plan gives.                                                                                                                                                                                                                                                                                                    |

<Callout type="warning" title="Over the plan, your workspaces publish nothing">
  If your plan shrinks below what you hold, nothing is deleted. But until the
  channels you hold are back within it, by disconnecting some or adding a
  payment method, your workspaces schedule and publish nothing ([A workspace
  over its plan](/guides/workspace/billing#over)).
</Callout>

A self-hosted Peal without billing limits nothing. `GET /api/v1/partner` answers what the account holds each day, and [its usage per customer](#usage) what each workspace used. That's what a price per workspace or per connected channel would count.

A partner key with the scope `workspaces:read` reads it at `GET /api/v1/partner/customer-usage`. Your home workspace's owners and admins (`partner:read`) read it at `GET /api/v1/workspace/usage/partner`, which answers the same, as do the command line and the MCP tool. Any other workspace answers 404 `PartnerNotFound`.

`from` and `to` are UTC days, both included, 92 days at most. By default you get the 30 days that end today.

The answer has these fields:

| Field        | What it holds                                                                                                                                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| `current`    | The workspaces you own now, and the channels connected across them and your home workspace, which your plan's channel limit counts             |
| `days`       | For each day, the workspaces and channels as the daily count found them at 23:41 UTC (null for a day without one), and the posts that went out |
| `totals`     | The period's posts by platform, its channel-days and, for each calendar month it touches, the posts on platforms that bill per post            |
| `workspaces` | A page of workspaces, [below](#usage-workspaces)                                                                                               |

`current`, `days` and `totals` cover the whole account, so they come with the first page only. They're `null` on the pages after it, which read their own workspaces alone.

### Per workspace [#usage-workspaces]

`workspaces` is a page of them, in the order and with the cursor of [`GET /api/v1/partner/workspaces`](/developers/embedding#workspaces): newest first, 50 a page unless `limit` says otherwise (100 at most). Pass `next` as `before` for the next page. Your home workspace comes first, on the first page only, with `home: true`, one more than you asked for.

Each one gives its `externalId` and the channels it connected itself now. Over the period, it gives its channel-days, its posts by platform, its requests to the writing assistant, its latest media storage and its metered posts.

A customer offboarded during the period is no longer listed, and its posts leave the sums, because its counts were erased with it. The daily `workspaces` and `channels` still count it for the days it existed.

The daily counts are kept {{keep-partner-usage-en}}. They're counts only, and nothing here is priced. A self-hosted Peal without billing answers `plan` and `allowances` as null.

## Where things are [#surfaces]

Each task has its place, depending on whether your backend or a person does it:

| To                                              | Use                                                                                                                                                                                             |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Set the account up, create and revoke keys      | The web app: **Settings**, then **Partner**                                                                                                                                                     |
| Create, find, change and delete workspaces      | `/api/v1/partner`, with a partner key; `partner` in the SDKs                                                                                                                                    |
| Act inside a workspace                          | `/api/v1/…`, with the same key; `channels.connectLinks`, `channels`, `media`, `posts`, `analytics` in the SDKs                                                                                  |
| Read the account and its workspaces as a person | `peal partner show`, `peal partner keys`, `peal partner workspaces` ([command line](/developers/cli/workspace#partner))                                                                         |
| Read the usage per customer                     | `GET /api/v1/partner/customer-usage`, with the key; `partner.customerUsage` in the SDKs; `peal partner usage`, the MCP tool `get_partner_usage` and **Settings**, then **Partner**, as a person |
| See which customers need attention              | `GET /api/v1/partner/overview`, with the key; `partner.overview` in the SDKs; `peal partner overview` and **Settings**, then **Partner**, as a person ([Health](#health))                       |
| Make a link by hand for a workspace of yours    | `peal links create` ([command line](/developers/cli/workspace#links)), or the MCP tool `create_connect_link` ([MCP](/developers/mcp/tools#tools))                                               |

The [API reference](/reference) lists every endpoint with its errors. The [SDKs](/developers/sdks) are generated from the same contract, in eight languages. A partner key can check itself with `GET /api/v1/credential` (`credential.get`), which names its partner, scopes and permissions, and never its workspaces.

### Without a partner account [#agencies]

Connect links work in any workspace. A member who may connect channels, or an API key with `channel:connect`, can create one to hand to whoever owns an account, such as an agency's client. Such a link takes no `returnUrl`, and its page ends by saying the account is connected.

## Not there yet [#later]

These parts of embedding aren't built:

- Your own account picker. The choice among several accounts happens on Peal's hosted page.
- Your own platform apps. Your customers authorize Peal's app on each platform, and the platform's consent screen shows its name.
- Your own domain for the hosted pages, and pages without Peal's name.
