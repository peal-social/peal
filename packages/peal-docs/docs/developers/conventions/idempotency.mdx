## Idempotency [#idempotency]

When a request times out or the connection drops, you can't tell whether Peal created the post. Send an `Idempotency-Key` header and you can retry without posting twice.

The key is any text you pick, 255 characters at most, such as a UUID. Use a new one for each post. Keys are kept per workspace.

On `POST …/posts/send`, which creates a post and sends it, a key works like this:

- Within 24 hours, the same key with the same body answers the post the first request made, as it now stands, and makes no other.
- The same key with another body answers 409 `idempotency_key_reused`, and makes nothing.
- Once that post was deleted, the key answers 404 `post_not_found`.

### Requests that take a key [#keyed]

These requests take a key:

| Request                                     | The key                                                                                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST …/posts/send`                         | Optional, as above.                                                                                                                                                                                                                                                                                                                                                                      |
| `POST …/posts/bulk`, `POST …/posts/import`  | Optional, for the whole request, and each of their items or rows may carry a key of its own ([Posting through the API](/developers/posting)).                                                                                                                                                                                                                                            |
| Creating a customer's workspace             | Optional, through the partner API ([Embedding Peal](/developers/embedding)).                                                                                                                                                                                                                                                                                                             |
| `POST …/inbox/comments/{commentId}/replies` | Optional. It answers a comment in public. Within 24 hours, the same key with the same comment and text answers the reply the first request made, however it stands, and writes no other. With another comment or text it answers 409 `idempotency_key_reused`. Without a key, a second request is refused (409 `reply_pending`) only while the first reply is on its way or unconfirmed. |
| `POST …/ads/boosts`                         | Required, because it spends money. The same key with the same request answers the boost it made and never makes another, and with another request answers 409 `boost_key_reused` ([Ads](/developers/ads#api-boost)).                                                                                                                                                                     |

### Requests without a key [#unkeyed]

The other writes take no key. Whether you can safely send one again depends on what it does:

| Request                                                                           | Sent again                                                                                                                                                                                        |
| --------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Reads (`GET`)                                                                     | Safe.                                                                                                                                                                                             |
| `PUT`, `PATCH` and `DELETE`                                                       | Safe: they set a resource to what the request says, or remove it. A second `DELETE` answers 404, except removing a channel from a post, which answers the post again.                             |
| Scheduling, moving, unscheduling or cancelling a post, confirming a target        | Safe: they act on one post, by its id, which goes out once however often it is scheduled. A repeat changes nothing more, or answers 409 with the `status` the post has.                           |
| Creating a draft, importing media, adding a webhook endpoint, creating an API key | Makes another one. None of them puts anything out, so list what the workspace has before sending again, and delete a duplicate.                                                                   |
| Inviting someone                                                                  | Replaces the pending invitation to that address, and emails it again.                                                                                                                             |
| Reposting a target (`POST …/posts/{postId}/targets/{targetId}/repost`)            | Not safe: each repost sends the post again on that channel. Read the post first: only a target that failed or is unconfirmed can be reposted, and any other answers 409 `target_status_conflict`. |

### Unconfirmed outcomes [#unconfirmed]

Peal has the same problem with the platforms. When a platform's answer is lost, Peal looks the post up there, where the platform allows it. When it still can't tell whether the post went out, the target is `unconfirmed`. Peal doesn't send it again, because a second attempt could show the post twice.

<Callout type="warning" title="Never repost an unconfirmed target blindly">
  If the first attempt went out, a repost shows the post twice. Have someone
  look on the platform first. Then record what they found with `…/targets/
  {targetId}/confirm`, or repost ([Follow up on a
  post](/guides/posts/schedule#follow-up)).
</Callout>

Each publishing attempt, in `GET …/posts/{postId}/attempts`, says how it ended in `result`. Its `refusalCode` holds the code behind a refusal: the platform's own, as it gave it, or Peal's when Peal refused before calling the platform. It's `null` when there's none.

The platforms' codes are theirs and change with them. Show them and log them, but branch on `result`.
