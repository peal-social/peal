Every error the API answers has the same shape, so a client handles them all in one place. This page describes that shape, says what to do with each status, and lists every code.

## Errors [#errors]

Every error is a JSON object with the same four fields, then the error's own:

| Field       | What it holds                                                                                                                                    |
| ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `code`      | The error's name for programs, in snake case, such as `post_not_found`. It never changes once published: branch on it.                           |
| `_tag`      | The same name as clients generated from the contract match on it, such as `PostNotFound`. It never changes either.                               |
| `message`   | One or two sentences in English, for the person reading a log or a terminal. Its wording may change: never parse it.                             |
| `requestId` | The request's id, as its `X-Request-Id` header gives it.                                                                                         |
| others      | What the error says of itself, as the reference lists for each: the `status` a post has, the `limit` a plan reached, the `violations` of a post. |

<Callout type="info">
  Two families of routes answer differently, as their own clients expect: the
  sign-in service's routes under `/api/auth`, and the [MCP
  endpoint](/developers/mcp), which answers JSON-RPC errors. Their answers carry
  `X-Request-Id` too.
</Callout>

### What to do with an error [#handling]

| Answer                        | What it means                                                                                              | What a client does                                                                                                                                            |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400                           | The request is wrong.                                                                                      | Fix it as `issues` or `message` say. Sending it again unchanged fails again.                                                                                  |
| 401                           | The credential does not work.                                                                              | Renew the access token with the refresh token, or use a key that works.                                                                                       |
| 402 `plan_limit_reached`      | The workspace's plan has no room.                                                                          | Tell the person: `planWithRoom` and `billingUrl` say where to go. Do not retry.                                                                               |
| 402 `usage_allowance_reached` | A meter of the billing account is used for the month.                                                      | Tell the person: `reason` and `billingUrl` say what to do; else wait for `resetsAt`. Do not retry before.                                                     |
| 403                           | The credential does not allow it.                                                                          | Read `reason`. Do not retry until the scope or the permission is given.                                                                                       |
| 404                           | Nothing there for this caller.                                                                             | Check the ids and the workspace. Do not retry.                                                                                                                |
| 409                           | What the request acts on is not in a state that allows it.                                                 | Read it again, then decide: a post already scheduled needs no second request.                                                                                 |
| 413, 422                      | The content was refused.                                                                                   | Fix it as the error's fields say: `violations`, `channelIds`, `mediaIds`, `reason`.                                                                           |
| 429 `too_many_requests`       | The credential passed its [rate limit](/developers/conventions/rate-limits#rate-limits). Nothing was done. | Wait as `Retry-After` says, then send the request again.                                                                                                      |
| 429, another code             | A limit of one feature, such as the assistant's daily requests.                                            | Wait as the error says (`resetsAt`), or a moment for `media_import_busy`.                                                                                     |
| 500 `internal_error`          | The server failed, and recorded it.                                                                        | Retry a read. For a write, read what it acts on first: it may have been applied. Resend `posts.send` only with the same `Idempotency-Key`. Quote `requestId`. |
| 502, 503                      | The server, or a service it needs, cannot answer for now.                                                  | Retry with a growing delay, a few times, under the same `Idempotency-Key` where the endpoint takes one.                                                       |

### A request that cannot be read [#invalid-request]

A request that does not match what its endpoint takes answers 400 `invalid_request`, and nothing was done.

- `issues` lists what was found wrong, 20 problems at most. Each has a `path`, which starts with the part of the request (`path`, `query`, `headers` or `body`) and goes down to the value, and a `message`.
- `field` is the first problem's path, dotted.
- Reading may stop at the first problem, so fixing what is listed can show another.

```bash
curl -i "https://api.example.com/api/workspaces/$WORKSPACE_ID/media?limit=500" \
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```http
HTTP/1.1 400 Bad Request
Content-Type: application/json
X-Request-Id: 019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37
```

```json
{
  "_tag": "InvalidRequest",
  "code": "invalid_request",
  "message": "The request does not match what the endpoint takes: `issues` says what and where. Nothing was done.",
  "requestId": "019a7b2e-5c1d-7f3a-9e42-8b6d0c1a2f37",
  "field": "query.limit",
  "issues": [
    {
      "path": ["query", "limit"],
      "message": "Expected a value between 1 and 100"
    }
  ]
}
```

A value of the right shape that cannot be used where it was sent, such as a cursor taken from another list, answers 400 `bad_request`.

### A request that is not allowed [#forbidden]

A 403 says why in `reason`, names the `permission` the request takes when one is missing, and the `scope` to ask for when an OAuth application lacks it. Its `message` says how to get what is missing.

| `reason`            | Why                                                                                                                                                    | What to do                                                                                                                                                  |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `missingScope`      | The member may do this, but did not give the application the scope it takes (`scope`).                                                                 | The member connects the application again and allows it; `peal login` for the command line.                                                                 |
| `missingPermission` | The member's role, or the API key, lacks `permission`.                                                                                                 | An owner or an admin changes the role, or creates a key that has it.                                                                                        |
| `personRequired`    | Only a person in their own session does this, in the web app.                                                                                          | Nothing a key or an application can do.                                                                                                                     |
| `wrongWorkspace`    | The key or the token belongs to another workspace.                                                                                                     | Use it there, or use a credential of this workspace.                                                                                                        |
| `suspended`         | The account is suspended.                                                                                                                              | Write to the people who run the server.                                                                                                                     |
| `untrustedOrigin`   | A browser sent the session's cookie from another site.                                                                                                 | Send an API key or an OAuth token instead.                                                                                                                  |
| `twoStepRequired`   | The workspace requires two-step verification, and the member's account does not have it on; or, on the staff console, the server requires it of staff. | The person turns it on in their [account settings](/guides/workspace/account#two-step); the same token then works again. API keys are never refused for it. |

A token that lacks a scope also gets the challenge OAuth clients read, in `WWW-Authenticate`:

```bash
curl -i -X POST https://api.example.com/api/workspaces/$WORKSPACE_ID/posts/019a6c3f-1b72-7d3c-8e90-4f5a6b7c8d02/cancel \
  -H "Authorization: Bearer $PEAL_ACCESS_TOKEN"
```

```http
HTTP/1.1 403 Forbidden
Content-Type: application/json
WWW-Authenticate: Bearer error="insufficient_scope", scope="workspace:publish"
X-Request-Id: 019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68
```

```json
{
  "_tag": "Forbidden",
  "code": "forbidden",
  "message": "This application was not given the scope workspace:publish (schedule and publish posts), which this request takes (permission post:schedule). Its user connects it to Peal again and allows it; for Peal's command line, run peal login again and approve it.",
  "requestId": "019a7b2f-9a04-7b61-8c3d-2e5f7a1b4c68",
  "reason": "missingScope",
  "permission": "post:schedule",
  "scope": "workspace:publish"
}
```
