Les paramètres d’un espace de travail appartiennent à ses membres, et votre rôle décide de ceux que vous pouvez changer. [Ceux de votre compte](/guides/workspace/account) n’appartiennent qu’à vous, dans tous vos espaces.

## Trouver les paramètres [#workspace]

Dans un espace de travail, cliquez sur **Paramètres** en bas de la barre latérale. La barre liste alors les pages de paramètres, et vous voyez celles que votre rôle vous permet d’ouvrir :

| Page            | Qui la voit                                |
| --------------- | ------------------------------------------ |
| **Général**     | Chaque membre                              |
| **Membres**     | Chaque membre                              |
| **Sécurité**    | Chaque membre                              |
| **Invitations** | Les membres qui peuvent inviter            |
| **Assistant**   | Les propriétaires et les administrateurs   |
| **Clés d’API**  | Les membres qui peuvent gérer les clés     |
| **Webhooks**    | Les membres qui peuvent gérer les webhooks |

**Clés d’API** et **Webhooks** ne sont pas sous **Paramètres**. Passez la barre latérale de **Studio** à **Console** pour les trouver sous **Développer**, avec **Partenaire** sous **Partenaires**.

Voici ce que chaque rôle peut faire dans les paramètres :

| Rôle           | Dans les paramètres                                                                                                                                                                                                                               |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Propriétaire   | Tout : renommer, les membres, propriétaires compris, les invitations, les clés d’API, les webhooks, les fournisseurs d’images et de texte de l’assistant, l’exigence de la validation en deux étapes, et la suppression                           |
| Administrateur | Renommer, les membres autres que les propriétaires, les invitations, les clés d’API, les webhooks et les fournisseurs d’images et de texte de l’assistant. Jamais les propriétaires, l’exigence de la validation en deux étapes ni la suppression |
| Éditeur        | Voit les membres                                                                                                                                                                                                                                  |
| Contributeur   | Voit les membres                                                                                                                                                                                                                                  |
| Lecteur        | Voit les membres                                                                                                                                                                                                                                  |

Sous **Général**, les propriétaires et les administrateurs règlent aussi **Approbations**, qui décide si les publications attendent une approbation avant d’être programmées. Voyez [Relecture et approbation](/guides/posts/review#policy).

### Gérer les membres [#members]

**Membres** liste toutes les personnes de l’espace de travail, avec leur rôle. Si vous êtes propriétaire ou administrateur, vous pouvez :

- Changer le rôle d’un membre depuis la liste.
- Cliquer sur **Retirer** pour faire sortir quelqu’un de l’espace. Vous confirmez d’abord, et la personne perd l’accès aussitôt.

Seuls les propriétaires peuvent nommer ou retirer un propriétaire. Un espace de travail garde toujours au moins un propriétaire. Le dernier ne peut donc ni quitter ce rôle ni être retiré.

### Inviter des personnes [#invitations]

<Steps>
<Step title="Envoyer l’invitation">

Sous **Invitations**, saisissez une adresse e-mail et sélectionnez un rôle, puis cliquez sur **Envoyer l’invitation**. Seuls les propriétaires peuvent inviter des propriétaires.

</Step>
<Step title="La personne rejoint l’espace">

Elle reçoit un lien pour rejoindre l’espace, valable 7 jours. Il est dans sa langue si elle a déjà un compte, et dans la vôtre sinon. Elle rejoint l’espace une fois connectée avec cette adresse.

</Step>
</Steps>

Les invitations en attente sont listées avec leur date d’expiration. Pour chacune, vous pouvez :

- Cliquer sur **Renvoyer** pour envoyer de nouveau le lien par e-mail, valable 7 jours de plus.
- Cliquer sur **Révoquer** pour rendre le lien inutilisable.
- Cliquer sur **Copier le lien** pour copier ce même lien, dans votre langue, et le transmettre autrement.

Seule la personne invitée peut l’accepter, connectée avec l’adresse invitée une fois celle-ci vérifiée, et seulement jusqu’à l’expiration de l’invitation.

### Exiger la validation en deux étapes [#require-two-step]

Sous **Sécurité**, un propriétaire peut exiger la [validation en deux étapes](/guides/workspace/account#two-step) de tous les membres. Il faut un propriétaire connecté lui-même. Un administrateur ne le peut pas, ni une clé d’API, une application ou l’équipe agissant à la place d’un propriétaire. Vous devez aussi l’avoir activée pour votre propre compte, pour ne pas vous enfermer dehors.

<Callout
  type="warning"
  title="Les membres qui ne l’ont pas perdent l’accès aussitôt"
>
  Avant que l’exigence ne s’applique, Peal nomme les membres dont le compte ne
  l’a pas activée. Ils perdent l’accès tout de suite, jusqu’à ce qu’ils
  l’activent.
</Callout>

Chaque membre voit si elle est exigée. Ceux qui gèrent les membres voient qui l’a activée, dans **Membres**.

Un membre dont le compte ne l’a pas activée se voit refuser l’espace partout où il l’atteint :

- L’application web lui montre ce qu’exigent les propriétaires et un chemin vers les paramètres de son compte, au lieu de toute page de l’espace.
- La [ligne de commande](/developers/cli#login) et les [clients MCP](/developers/mcp#sign-in) sont refusés avec `twoStepRequired`.
- Les routes d’espace de travail du service de connexion le refusent aussi pour cet espace.

Ses sessions et applications restent connectées, et tout fonctionne de nouveau dès qu’il l’active. Les invitations fonctionnent toujours : la personne rejoint l’espace, puis Peal lui demande de l’activer. Les [clés d’API](#api-keys) de l’espace et les clés d’un partenaire ne sont pas concernées, car elles appartiennent à l’espace, pas à une personne.

Ne plus l’exiger s’applique aussitôt aussi. Les deux changements sont inscrits au [journal d’activité](#activity).

### Créer une clé d’API [#api-keys]

<Steps>
<Step title="Créer la clé">

Sous **Clés d’API**, donnez un nom à la nouvelle clé, choisissez sa durée de validité (30, 90 ou 365 jours, ou jusqu’à révocation) et ce qu’elle peut faire. Vous ne pouvez lui donner que des permissions que votre propre rôle possède.

</Step>
<Step title="La copier">

La clé s’affiche une seule fois, juste après sa création. Copiez-la à ce moment-là, car Peal n’en garde qu’une empreinte. [La présentation de l’API](/developers#authentication) montre comment l’envoyer.

</Step>
</Steps>

Cliquez sur **Révoquer** pour arrêter une clé aussitôt. L’équipe qui agit à la place d’un membre ne voit ni ne gère les clés.

La liste indique pour chaque clé si elle **Peut programmer et publier des publications**. C’est le cas quand elle porte `post:schedule`, `post:publish` ou `post:approve`. Sans elles, elle écrit tout au plus des brouillons. Une publication créée ou programmée avec une clé le dit sur sa page, avec le nom de la clé.

<Callout type="warning" title="Ce qu’une clé publie est public">
  Ne donnez ces permissions à une clé que si ce qui l’utilise doit publier. Ce
  qu’elle envoie est public sur les plateformes ([Publier depuis un agent
  IA](/developers/agents#api)).
</Callout>

### Ajouter des webhooks [#webhooks]

Sous **Webhooks**, les propriétaires et les administrateurs ajoutent les adresses que Peal appelle quand il se passe quelque chose dans l’espace de travail, 10 au plus. Chaque point de terminaison a :

- les événements qu’il veut recevoir et une description
- un secret de signature, qui s’affiche une seule fois, juste après la création du point de terminaison ou le renouvellement de son secret
- un journal de ses livraisons, gardé 30 jours, d’où vous pouvez renvoyer une livraison
- un événement de test que vous pouvez lui envoyer.

L’équipe qui agit à la place d’un membre ne peut pas changer les webhooks. [Webhooks](/developers/webhooks) liste les événements et montre comment vérifier une livraison.

### Utiliser votre propre fournisseur d’images [#image-provider]

Sous **Assistant**, les propriétaires et les administrateurs peuvent régler le fournisseur d’images de l’espace de travail. Les [images que crée l’assistant](/guides/media#generate) viennent alors de votre compte chez lui, au lieu du modèle de l’instance. Le régler demande `assistant:configure`, qui peut aussi être donné à une [clé d’API](#api-keys) ou à une [clé partenaire](/developers/embedding#account).

Remplissez trois champs :

| Champ       | Ce qu’il faut saisir                                                                                                                                                                                                                                                                                                                                                                                                                     |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Adresse** | L’adresse de base d’un point d’accès qui parle l’API d’images d’OpenAI, celle à laquelle Peal ajoute `/images/generations`, par exemple `https://images.example.com/v1`. Beaucoup de fournisseurs en proposent une, dite « compatible OpenAI ». Peal envoie une seule forme de requête, `{ model, n, prompt, size }`, et lit en retour une image en base64 ou à une adresse. Il ne peut pas promettre qu’un fournisseur donné l’accepte. |
| **Modèle**  | Le modèle de votre fournisseur, tel que sa documentation le nomme. Vous pouvez changer le modèle seul.                                                                                                                                                                                                                                                                                                                                   |
| **Clé**     | La clé de votre compte chez le fournisseur, envoyée comme jeton porteur. Peal la garde chiffrée, pour cet espace de travail et cette adresse exacte seulement. Une clé enregistrée s’affiche comme enregistrée et reste tant que vous n’en saisissez pas une autre.                                                                                                                                                                      |

L’adresse doit être en HTTPS sur le port par défaut, sur un hôte public, sans nom d’utilisateur, mot de passe, requête ni fragment.

Peal ne montre plus jamais la clé et ne l’écrit jamais dans ses journaux. Tout changement de l’adresse, de son hôte ou de son chemin redemande la clé, car Peal n’envoie jamais une clé à une adresse pour laquelle elle n’a pas été donnée.

Une fois le fournisseur enregistré, les descriptions d’images de l’espace de travail partent à cette adresse avec cette clé. Le modèle de Peal ne leur est jamais demandé, même quand votre fournisseur refuse. À quoi vous attendre :

- Ses images ne consomment aucune des demandes à l’assistant de l’espace de travail, quel que soit l’abonnement, gratuit et essai compris, jusqu’à 50 par jour. Elles occupent toujours le stockage de l’abonnement.
- Peal n’appelle pas le fournisseur à l’enregistrement. La première image vous dit si les réglages fonctionnent.
- Quand le fournisseur refuse la clé, le compte, le modèle ou l’adresse, aucune image n’est créée et la fenêtre le dit.
- Quand les clés de l’instance changent et que la clé enregistrée ne peut plus être lue, la page la redemande.
- Cliquez sur **Retirer** et confirmez pour supprimer la clé. Les images viennent alors de nouveau du modèle de l’instance, s’il en a un.

La [ligne de commande](/developers/cli/posts#assistant) a `peal assistant image-provider`. Aucun outil MCP ne le lit ni ne le règle, car une clé saisie dans une conversation atteint un modèle.

<Accordion>
<AccordionItem title="Les adresses que Peal refuse">

Peal refuse une adresse, et dit pourquoi en toutes lettres, avec l’un de ces codes :

| Code              | L’adresse                           |
| ----------------- | ----------------------------------- |
| `notHttps`        | n’est pas en HTTPS                  |
| `credentials`     | contient des identifiants           |
| `queryOrFragment` | contient une requête ou un fragment |
| `tooLong`         | est trop longue                     |
| `malformed`       | n’est pas une adresse               |
| `notPublic`       | a un hôte qui n’est pas public      |
| `unknownHost`     | a un hôte qui ne se résout pas      |

Un serveur dont l’opérateur n’a pas défini de clés pour chiffrer les secrets ne garde aucune clé (`AssistantSecretsNotConfigured`).

</AccordionItem>
</Accordion>

### Utiliser votre propre fournisseur de texte [#text-provider]

Sous **Assistant**, les propriétaires et les administrateurs peuvent aussi régler le fournisseur de texte de l’espace de travail. L’[assistant de rédaction](/guides/posts/assistant#assistant) écrit alors avec votre compte chez lui, au lieu du modèle de l’instance. C’est ainsi qu’un espace de travail utilise l’assistant hors de l’allocation de l’instance : ses demandes n’y sont pas comptées, quel que soit l’abonnement.

Remplissez quatre champs :

| Champ       | Ce qu’il faut saisir                                                                                                                                                                                                                                                                                                                                                  |
| ----------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **API**     | **Anthropic** (l’API Messages d’Anthropic : Peal ajoute `/v1/messages` à l’adresse et envoie la clé dans `x-api-key`) ou **Compatible OpenAI** (tout point d’accès qui sert l’API de complétions de conversation : Peal ajoute `/chat/completions` et envoie la clé comme jeton porteur).                                                                             |
| **Adresse** | `https://api.anthropic.com` pour Anthropic, que la page remplit pour vous. Pour un point d’accès compatible OpenAI, l’adresse que suit `/chat/completions`, par exemple `https://text.example.com/v1`. Les règles du fournisseur d’images s’appliquent : HTTPS sur le port par défaut, sur un hôte public, sans nom d’utilisateur, mot de passe, requête ni fragment. |
| **Modèle**  | Le modèle de votre fournisseur, tel que sa documentation le nomme. L’assistant lui demande une sortie structurée (une réponse qui suit un schéma JSON). Un modèle qui ne sait pas en donner échoue donc à chaque demande.                                                                                                                                             |
| **Clé**     | La clé de votre compte chez le fournisseur. Peal la garde et l’affiche comme celle du fournisseur d’images : chiffrée, pour cet espace de travail et cette adresse exacte seulement, jamais montrée de nouveau, jamais journalisée, et redemandée quand l’adresse change.                                                                                             |

Une fois le fournisseur enregistré, les textes sur lesquels les membres sollicitent l’assistant, et les sujets des publications qu’il rédige, partent à cette adresse avec cette clé, selon les conditions de ce fournisseur. Le modèle de l’instance ne leur est jamais demandé, même quand votre fournisseur refuse. À quoi vous attendre :

- Ces demandes ne consomment aucune des demandes à l’assistant de l’espace de travail, jusqu’à 500 par jour. Chacune compte, quelle que soit son issue.
- Quatre au plus partent à la fois. Une cinquième envoyée entre-temps est refusée (`TextProviderBusy`) et ne compte pas.
- Cliquez sur **Tester** pour envoyer à votre fournisseur une courte demande, la réécriture d’une phrase fixe. Peal dit s’il a répondu par une suggestion que l’assistant peut utiliser, ou pourquoi non. Le test compte parmi les 500.
- Quand votre fournisseur refuse la clé, le compte, le modèle ou l’adresse, l’assistant le dit, et rien de l’allocation de l’instance n’est dépensé.
- Cliquez sur **Retirer** et confirmez pour supprimer la clé. L’assistant utilise alors de nouveau le modèle de l’instance, s’il en a un, dans l’allocation de l’espace de travail.

### Qui peut régler les fournisseurs [#providers-access]

Seuls ceux-ci peuvent régler les fournisseurs d’images et de texte :

- un membre, dans sa propre session
- la [ligne de commande](/developers/cli/posts#assistant) de Peal (`peal assistant text-provider`)
- une [clé d’API](#api-keys) ou une [clé partenaire](/developers/embedding#account) à qui `assistant:configure` a été donné.

Aucune autre application connectée par OAuth ne détient cette permission, un client [MCP](/developers/mcp) compris, quelles que soient les permissions qui lui ont été accordées. Aucune ne peut donc envoyer les brouillons de l’espace de travail à une adresse à elle. L’équipe qui agit à la place d’un membre ne peut ni régler les fournisseurs ni leur demander quoi que ce soit, car le compte de l’espace de travail chez le fournisseur paierait.

### Lire le journal d’activité [#activity]

Chaque espace de travail tient le journal de qui a changé quoi, et par quelle application. Il inscrit :

- chaque requête qui a demandé à changer quelque chose dans l’espace, qu’elle ait abouti ou été refusée
- chaque appel d’un outil [MCP](/developers/mcp) qui change quelque chose.

Les requêtes qui ne font que lire n’y figurent pas, ni celles qui vérifient sans rien créer, comme valider une publication ou importer un fichier à blanc. Une requête qui crée plusieurs publications d’un coup (`posts.bulk`, `posts.import`) est un seul événement, quoi qu’elle ait créé.

Seuls les propriétaires peuvent lire le journal. Il demande la permission `activity:read`, que seul le rôle de propriétaire porte. Un propriétaire peut donner cette permission à une [clé d’API](#api-keys), et une application qu’un propriétaire a connectée lit le journal comme lui.

Le journal n’a pas encore de page dans l’application web. Vous pouvez le lire de trois façons :

- par l’API, avec `GET /api/workspaces/{workspaceId}/activity`, les plus récents d’abord, page par page ([Pagination](/developers/conventions/paging#paging) montre une réponse)
- depuis la [ligne de commande](/developers/cli/workspace#activity), avec `peal activity list`
- depuis un client MCP, avec l’outil `list_activity`.

Pour le restreindre, `operation` ne garde que les événements d’une opération, comme `posts.schedule`. `actor` garde ceux qu’a demandés un membre, désigné par son identifiant d’utilisateur, ou une clé d’API, désignée par le sien.

Chaque événement a ces champs :

| Champ          | Ce qu’il contient                                                                                                                                                                                                                                                                                                                                                                                 |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `occurredAt`   | Quand.                                                                                                                                                                                                                                                                                                                                                                                            |
| `operation`    | Le point d’accès, tel que la référence le nomme (`posts.schedule`, `channels.disconnect`). Pour un outil MCP, `mcp.` suivi de son nom (`mcp.create_draft`). Pour ce que les réglages de l’application web changent par le service de connexion (un rôle, un membre retiré, une invitation, l’abonnement), `auth:` suivi de son chemin (`auth:/organization/remove-member`).                       |
| `status`       | Le statut HTTP répondu. `null` pour l’appel d’un outil MCP, qui n’en a pas.                                                                                                                                                                                                                                                                                                                       |
| `errorCode`    | Le [code d’erreur](/developers/conventions/errors#error-codes) quand la requête a été refusée ou a échoué, `null` quand elle a abouti. Pour un outil MCP, `tool_refused` quand l’outil a répondu par une erreur, et `tool_failed` quand l’appel s’est terminé sans réponse.                                                                                                                       |
| `actor`        | Qui a demandé : un membre (`user`, avec son `userId`) ou une clé (`apiKey`, avec son `apiKeyId`). Une clé est une clé d’API de l’espace de travail, une [clé partenaire](/developers/embedding), ou un [lien de connexion](/guides/channels#connect-links), noté `connect-link:` suivi de son identifiant. `via` dit laquelle. La personne qui a ouvert un lien de connexion n’est jamais nommée. |
| `via`          | Le moyen d’authentification : `session` (l’application web), `apiKey`, `oauth` (une application passant par l’API, comme la ligne de commande), `mcp`, `partnerKey` (une clé partenaire, dans un espace de travail que possède son compte partenaire) ou `connectLink` (un compte connecté sur la page d’un lien de connexion).                                                                   |
| `application`  | La clé ou l’application par laquelle la requête est passée, avec son `id` et le nom (`name`) qu’elle portait alors. `null` pour une personne dans l’application web.                                                                                                                                                                                                                              |
| `impersonated` | Si c’est l’équipe, agissant à la place du membre, qui a demandé. Jamais qui.                                                                                                                                                                                                                                                                                                                      |
| `objectIds`    | Les identifiants que nommait le chemin de la requête, comme `postId` ou `channelId`.                                                                                                                                                                                                                                                                                                              |
| `requestId`    | L’identifiant de la requête, tel que le donnait son en-tête `X-Request-Id` ([Requêtes et réponses](/developers/conventions#requests)).                                                                                                                                                                                                                                                            |

Le journal ne contient rien de plus. Il ne garde jamais ce qu’une requête ou sa réponse contenait, ni le texte d’une publication, ni une adresse, ni un navigateur.

Un événement est gardé {{keep-activity-fr}}, puis une tâche quotidienne le supprime. Supprimer l’espace de travail supprime son journal. Quand un membre ferme son compte, les événements qu’il a laissés dans les espaces qui restent y demeurent, sans son identifiant. L’[export](/guides/workspace/account#export) de chaque membre contient les changements qu’il a lui-même demandés.

### Gérer un compte partenaire [#partner]

Un compte partenaire permet à un de vos produits d’utiliser Peal pour ses propres clients. Sous **Partenaire**, les propriétaires et les administrateurs gèrent le compte partenaire de l’espace de travail. Ils règlent :

- ce que ces clients voient sur les pages hébergées : un nom, une **Adresse du logo** et une **Couleur d’accent**
- les **Origines de retour** vers lesquelles ces pages peuvent les renvoyer
- les clés partenaires, chacune affichée une seule fois, juste après sa création.

La page liste les espaces de travail les plus récents que possède le compte, avec leurs canaux. Pouvoir ouvrir un compte vous-même est le choix de l’instance. Si vous ne le pouvez pas, la page vous dit de le demander aux personnes qui l’exploitent.

Un compte ne se ferme qu’une fois qu’il ne possède plus aucun espace de travail. L’équipe qui agit à la place d’un membre ne peut pas le modifier. [Intégrer Peal](/developers/embedding) décrit tout le parcours.

### Supprimer un espace de travail [#delete-workspace]

Dans **Général**, les propriétaires cliquent sur **Supprimer cet espace de travail…**, puis saisissent son nom pour confirmer.

<Callout
  type="danger"
  title="La suppression d’un espace de travail est définitive"
>
  Tout son contenu disparaît, définitivement : ses canaux et leurs
  autorisations, ses publications, programmées ou non, et leurs statistiques, sa
  médiathèque et ses fichiers, ses notifications, son utilisation de l’assistant
  de rédaction, ce que Peal a enregistré de ses abonnements et de ses
  publications sur X, ses membres et invitations, et ses clés d’API, qui cessent
  aussitôt de fonctionner. Plus rien n’en est publié. Stripe garde les factures
  qu’il a émises.
</Callout>

Si l’une de ses publications est en cours d’envoi, la suppression attend. Réessayez quelques minutes plus tard.

L’espace de travail peut avoir un abonnement que Stripe peut encore facturer : actif, impayé ou suspendu, y compris un abonnement dont le paiement vient d’aboutir avant que Stripe n’en ait informé Peal. La fenêtre dit alors d’abord ce que la suppression en fait, et attend que vous cochiez **Résilier l’abonnement maintenant**. Voici ce que devient l’abonnement :

- Il est résilié immédiatement chez Stripe, et plus rien n’est facturé.
- La période déjà payée n’est pas remboursée. Il n’y a ni avoir au prorata ni facture de clôture, sauf quand la loi prévoit un remboursement.
- La page **Facturation** de l’espace de travail disparaît avec lui. Téléchargez donc d’abord vos factures depuis le portail de facturation. Stripe garde les factures qu’il a émises, comme le droit comptable l’exige (10 ans en France), et l’e-mail de confirmation dit à qui en demander une copie.

L’exception de la loi concerne les consommateurs. Si vous avez souscrit en tant que consommateur il y a moins de 14 jours, vous pouvez vous rétracter et être remboursé de la part non utilisée. Rétractez-vous d’abord, avec **Renoncer au contrat ici** sur la page de facturation de l’espace de travail (voir [Abonnements et facturation](/guides/workspace/billing)). Une fois l’espace de travail supprimé, demandez-le plutôt à la personne qui gère le serveur.

Pour cesser de payer en gardant l’espace de travail, résiliez plutôt l’abonnement depuis sa page **Facturation**. Il prend alors fin avec la période payée.

<Accordion>
<AccordionItem title="Paiements ouverts, pannes et plusieurs espaces de travail">

- Un paiement de l’espace de travail encore ouvert, dans un autre onglet par exemple, est clos chez Stripe quand l’espace de travail disparaît. Il ne peut donc plus être réglé ensuite.
- Quand Stripe ne peut pas être joint, rien n’est supprimé. Réessayez quelques minutes plus tard. Un abonnement résilié avant l’échec le reste, et réessayer ne résilie rien de plus.
- Fermer un compte qui supprime plusieurs espaces de travail abonnés liste chaque abonnement résilié, avec la page de facturation de son espace de travail, avant que vous ne cochiez la case.

</AccordionItem>

</Accordion>

Une fois l’espace de travail supprimé, Peal envoie une confirmation à votre adresse, dans votre langue.

## Dans tous vos espaces de travail [#across-workspaces]

À la connexion, ou quand vous allez à l’adresse de Peal, vous arrivez dans l’espace de travail que vous avez créé ou choisi en dernier, sinon dans le premier des vôtres. À l’inscription, une page à part vous demande de nommer votre premier espace de travail et de choisir son adresse. Il remplit les deux pour vous (_Espace d’Ada_, à `/espace-dada`), et vous pouvez changer l’un ou l’autre, tant qu’aucun autre espace n’a cette adresse. Si une invitation vous attend, vous rejoignez cet espace à la place. Vous pourrez changer le nom et l’adresse plus tard dans les réglages généraux de l’espace.

Pour créer un autre espace de travail, ouvrez le menu des espaces en haut de la barre latérale et cliquez sur **Nouvel espace de travail**, qui ouvre la même page, le nom vide. **Retour**, en haut, ramène à votre espace de travail. Les pages d’un espace ont une adresse tirée de son nom, comme `/acme-studio/posts`. Cette adresse ne change pas quand vous renommez l’espace, et les liens qui contiennent l’identifiant de l’espace, comme ceux des e-mails de Peal, mènent à la même page.

Votre compte et vos notifications sont à vous dans chaque espace de travail : ils sont sous **Paramètres** dans chacun, après les réglages de l’espace ([Compte](/guides/workspace/account), [Notifications](/guides/workspace/notifications)).

### Par l’API et la ligne de commande [#across-workspaces-api]

L’application n’a pas de page qui couvre tous les espaces, mais ces points d’accès disent ce qui demande votre attention dans chaque espace de travail (publications en échec, publications qui attendent une approbation, canaux à reconnecter, commentaires à traiter, espace au-delà de son offre), ce qui part dans l’ensemble, et ce que chacun a donné :

- `GET /api/me/overview`
- `GET /api/me/agenda`, avec `from` et `to` (à 31 jours d’écart au plus) et `workspaceIds` (séparés par des virgules)
- `GET /api/me/report`, avec `days` et `timeZone`
- `GET /api/me/report/export`

La ligne de commande les propose sous `peal overview`, `peal agenda` et `peal report` ([Ligne de commande](/developers/cli#across-workspaces)).

Ils répondent à une personne. Les clés d’API, qui appartiennent à un espace, reçoivent 403, tout comme les jetons OAuth liés à un seul espace, comme celui d’un client MCP. Aucun outil MCP ne lit dans tous les espaces, car une connexion agit dans l’espace que vous lui avez choisi.

## Par l’API [#api]

Ces points d’accès gèrent votre espace de travail et votre compte :

| Point d’accès                            | Ce qu’il fait                                                        |
| ---------------------------------------- | -------------------------------------------------------------------- |
| `DELETE /api/workspaces/{workspaceId}`   | Supprime l’espace de travail, avec son nom en `name` (propriétaires) |
| `GET /api/me/export`                     | Répond vos données sous forme de fichier JSON                        |
| `DELETE /api/me`                         | Supprime votre compte, avec son mot de passe en `password`           |
| `GET /api/me/connected-apps`             | Liste vos applications connectées                                    |
| `DELETE /api/me/connected-apps/{client}` | En révoque une                                                       |

Ils ne répondent qu’à vous, connecté à l’application web avec votre propre session. Les clés d’API, les jetons OAuth et l’équipe qui agit à votre place reçoivent 403. Vos données et la liste de vos applications connectées répondent aussi à la [ligne de commande](/developers/cli/workspace#account) (`peal account`), que vous connectez depuis votre propre terminal. Elles ne répondent jamais à un client MCP ni à un autre client OAuth.

Ces points d’accès gèrent les membres et les invitations :

| Point d’accès                                                   | Ce qu’il fait                                                    |
| --------------------------------------------------------------- | ---------------------------------------------------------------- |
| `GET /api/workspaces/{workspaceId}/members`                     | Liste les membres, à chaque membre                               |
| `GET /api/workspaces/{workspaceId}/invitations`                 | Liste les invitations en attente, à qui peut inviter             |
| `POST /api/workspaces/{workspaceId}/invitations`                | Invite un `email` avec un `role`, comme **Envoyer l’invitation** |
| `DELETE /api/workspaces/{workspaceId}/invitations/{invitation}` | Révoque une invitation en attente                                |

Ils répondent aux membres en personne, par l’application web, la ligne de commande ou un client MCP autorisé. Ils ne répondent jamais à une clé d’API ni à l’équipe qui agit à votre place.

Renommer un espace de travail, changer le rôle d’un membre et retirer un membre passent par les routes du service de connexion sous `/api/auth/organization/`. Les clés d’API passent par `/api/workspaces/{workspaceId}/api-keys`.
