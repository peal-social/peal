Une fois une publication en ligne, vous pouvez encore la supprimer de ses plateformes ou corriger son texte là où elle est publiée. Vous pouvez aussi faire partir ses liens raccourcis. Les exemples créent le client comme l’explique [Publier par l’API](/developers/posting#start).

## Dépublier une publication [#unpublish]

Dépublier supprime une publication de la plateforme d’un canal, pour tout le monde. Sur un fil, toutes les parties sont supprimées, la dernière d’abord ([Dépublier une publication](/guides/posts/published#unpublish)). Trois requêtes s’en chargent :

| Requête                                              | Ce qu’elle fait                                                                                                                                                                                                                                    |
| ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST …/posts/{postId}/targets/{targetId}/unpublish` | Supprime la publication de la plateforme d’un canal.                                                                                                                                                                                               |
| `POST …/posts/{postId}/unpublish`                    | Le demande pour chaque canal de la publication. Elle renvoie le changement de chaque canal (`changes`) à côté des raisons pour lesquelles les autres n’ont pas pu l’être (`refused`), si bien qu’un canal ne fait jamais échouer toute la requête. |
| `GET …/posts/{postId}/changes`                       | Liste les changements d’une publication, du plus récent au plus ancien, avec post:read.                                                                                                                                                            |

Les deux requêtes de dépublication demandent post:publish, et un client OAuth a besoin du scope `workspace:publish`.

<Callout type="warning" title="Dépublier est définitif">
  La publication est supprimée sur la plateforme, pour tout le monde.
</Callout>

La requête est acceptée (202) avec le changement. Une tâche supprime ensuite la publication, un appel à la fois avec les autres appels du canal. Ajoutez `?wait=<secondes>` (60 au plus) pour attendre qu’elle se termine et recevoir le changement tel qu’il est alors.

```ts Node.js
  targetId: "019a6f3e-8c2b-7d02-8a11-6e2f9b0c7d15",
  wait: "30",
});
```

Le `status` du changement dit où en est la suppression :

| `status`  | Signification                                                                                                                                                   |
| --------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pending` | Il reste des parties (`partsLeft`).                                                                                                                             |
| `done`    | Il n’en reste plus. La cible garde `status: published` et reçoit `removedAt`. `GET …/posts?removed=true` liste les publications supprimées d’au moins un canal. |
| `failed`  | Peal a renoncé, avec un `code` (`unavailable`, `rateLimited`, `channelUnavailable`, ou celui de la plateforme). Redemander supprime les parties restantes.      |

`alreadyGone: true` indique que la plateforme n’avait déjà plus une partie.

### Quand Peal ne peut pas dépublier [#unpublish-refused]

Avant d’appeler la plateforme, Peal refuse une requête impossible avec 409 `live_post_not_changeable`. Sa `reason` est l’une de celles-ci :

- `notPublished`, `alreadyRemoved` ou `changeInProgress`
- `noPlatformId`, pour une publication que quelqu’un a confirmée à la main
- `notSupported`, là où les capacités de la plateforme disent pourquoi, dans `livePost`
- `channelUnavailable` ou `boostRunning`
- `deletionWindowPassed`, là où la plateforme ne supprime une publication que pendant un temps après sa mise en ligne (48 heures sur Telegram)

`GET …/channels/capabilities` vous dit d’avance où Peal supprime des publications. `livePost.unpublish` dit s’il le fait, et `livePost.unpublishBlockedBy` (`noApi`, `permission` ou `unverified`) dit pourquoi il ne le fait pas. Les webhooks reçoivent `post.unpublished` ou `post.unpublish_failed` ([Webhooks](/developers/webhooks/events/posts#post-unpublished)).

## Modifier une publication en ligne [#edit-live]

`POST …/posts/{postId}/targets/{targetId}/edit` remplace le texte d’une partie d’une publication en ligne sur la plateforme d’un canal, pour tout le monde ([Modifier une publication en ligne](/guides/posts/published#edit-live)). `livePost.edit` dans les capacités dit où Peal modifie.

Le corps prend ces champs, au moins `text`, `bodyMarkdown`, `body` ou `options` :

| Champ          | Ce qu’il contient                                                                         |
| -------------- | ----------------------------------------------------------------------------------------- |
| `text`         | Le nouveau texte                                                                          |
| `part`         | La partie, comptée depuis 0. Omise, c’est la publication elle-même (la partie 0).         |
| `bodyMarkdown` | Sur un site web, le corps en Markdown, qui remplace le texte ([plus bas](#edit-website)) |
| `body`         | Sur un site web, un texte enrichi qui remplace le texte ([plus bas](#edit-website))       |
| `options`      | Sur un site web, ses options désormais, entières ([plus bas](#edit-website))              |

Sur un réseau social ou une messagerie, seul le texte change, jamais les médias, les options ni l’heure. Il faut post:publish, et un client OAuth a besoin du scope `workspace:publish`. Quelqu’un qui doit faire approuver ses publications ([approbations](/guides/posts/review)) ne peut pas modifier une publication en ligne.

Peal vérifie le texte comme il vérifie le texte de ce canal quand une publication est programmée, avertissement de contenu Mastodon compris. Un texte que la plateforme refuserait répond 422 `post_content_invalid` avec chaque violation, tout comme un texte fait seulement d’espaces. Un `text` vide répond 400 `invalid_request`.

La requête est acceptée (202) avec le changement (`kind: "edit"`). Une tâche fait la modification, et la relance comme une suppression. `?wait=<secondes>` attend qu’elle se termine. Le changement ne contient jamais le texte.

### Modifier une publication sur un site web [#edit-website]

Sur WordPress, WordPress.com, DEV et Hashnode, la modification remplace l’article que le site affiche. Donnez l’un de ces champs, et ce que vous ne donnez pas reste tel quel :

- `text`, le nouveau texte, que le site reçoit en paragraphes avec les images de la publication, comme à sa publication. Il remplace un texte enrichi par des paragraphes simples : envoyez `bodyMarkdown` ou `body` pour garder la mise en forme.
- `bodyMarkdown`, le corps en Markdown, lu comme celui d’une publication ([Publier sur un site web](/developers/posting/websites#markdown)), qui remplace le texte. Un corps refusé répond 422 `post_content_invalid` avec `bodyInvalid` et ses `problems`.
- `body`, un texte enrichi (le `RichText` de la référence de l’API), qui remplace le texte. Envoyez-le ou `bodyMarkdown`, jamais les deux. Peal répond le `text` du canal comme son texte brut, et ses `media` comme ses images.
- `options`, les options du site désormais, entières, avec leur `platform`. Une option absente est retirée sur le site : sans `coverMediaId`, l’article perd sa couverture. Un `siteStatus` absent est celui de la cible.

```json
{
  "options": {
    "platform": "wordpress",
    "title": "Doors open at 7 pm",
    "tags": ["Events"]
  }
}
```

Le site garde le statut de l’article et sa date : un brouillon y reste un brouillon. Un `siteStatus` autre que celui de la cible répond 422 `post_content_invalid` avec `optionInvalid`. La modification est vérifiée comme la programmation vérifie la publication : le titre reste nécessaire, les fichiers que le site n’a pas encore doivent être ceux de l’espace de travail et prêts (422 `unknown_media` sinon), sur un réseau social, un `body` est `bodyNotTaken` et des `options` sont `optionsNotTaken`. Un fichier que le site a déjà reçu pour cette publication n’est pas envoyé de nouveau. Un refus du site garde son code, précédé de la plateforme (`wordpress:rest_cannot_edit`).

### Quand la modification aboutit ou échoue [#edit-result]

Une fois la modification faite, le nouveau texte devient celui de cette partie sur ce canal (dans `content.overrides`, ou dans l’entrée de la partie dans `content.followUps`). Les autres canaux gardent le leur, et la cible reçoit un `editedAt`. Peal ne garde aucun texte précédent.

Un changement `failed` a son `code`, et vous pouvez le redemander. Le code est l’un de ceux-ci, ou celui de la plateforme :

- `postGone`, quand la plateforme n’a plus la publication
- `pollNotEditable`, pour une publication Mastodon avec un sondage
- `permissionDenied`, pour un canal Mastodon à reconnecter

Avant d’appeler la plateforme, Peal refuse avec 409 `live_post_not_changeable`, comme pour une suppression, avec `approvalRequired` comme `reason` supplémentaire. Une partie qui n’est pas en ligne sur ce canal est `noPlatformId`.

Les webhooks reçoivent `post.edited` ou `post.edit_failed` ([Webhooks](/developers/webhooks/events/posts#post-edited)), avec la partie mais jamais le texte. `livePost.edit` et `livePost.editBlockedBy` dans les capacités vous disent d’avance où Peal modifie.

## Liens courts [#short-links]

`shortenLinks` demande que les liens de la publication partent [raccourcis](/guides/posts/published#short-links), sur un serveur qui a des liens courts. `GET …/links/status` dit s’il en a, par quoi commence une adresse courte et quelle est sa longueur.

Le champ fonctionne de la même façon sur `POST …/posts/drafts`, `PUT …/posts/{postId}`, `POST …/posts` et chaque élément de `bulk` :

| `shortenLinks` | Ce qui se passe                                                                                                                                                                  |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `true`         | Les liens partent raccourcis.                                                                                                                                                    |
| `false`        | Les liens partent tels qu’écrits.                                                                                                                                                |
| Omis           | Une nouvelle publication prend le choix par défaut de l’espace de travail (`byDefault` dans le statut) à sa création, et le garde. Un brouillon modifié garde son choix d’avant. |

Chaque publication porte `shortenLinks` dans sa réponse.

<Callout
  type="warning"
  title="Omettre le champ vaut désormais le choix de l’espace de travail"
>
  Il valait `false` pour toute publication sauf celles de l’application web. Dès
  qu’un espace de travail active le choix par défaut, les liens de ses
  publications faites par l’API, MCP, la ligne de commande et les flux partent
  raccourcis aussi. Envoyez `shortenLinks: false` quand les liens d’une
  publication doivent partir tels qu’écrits.
</Callout>

Ailleurs, les liens courts fonctionnent ainsi :

- `validate` prend le champ, et vérifie le texte tel qu’écrit, puisqu’une adresse courte ne l’allonge jamais.
- Un import CSV n’a pas de colonne pour lui : chaque ligne prend le choix par défaut de l’espace de travail.
- `GET …/links` lit les liens et leurs clics ([Clics sur les liens courts](/guides/engage/analytics#short-links)). Aucun point d’accès ne raccourcit une adresse hors d’une publication.
