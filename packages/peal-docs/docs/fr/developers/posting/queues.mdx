Vous pouvez laisser Peal choisir l’heure d’une publication sur le prochain créneau libre d’une file, faire se répéter une publication, la relancer quand elle marche bien, ou transformer un flux web en publications. Les exemples créent le client comme l’explique [Publier par l’API](/developers/posting#start).

## Ajouter une publication à une file d’attente [#queues]

Une file d’attente est un emploi du temps hebdomadaire de créneaux dans un fuseau horaire ([Files d’attente](/guides/posts/queues#queues)). Vous gérez les files avec `GET` et `POST …/queues`, et `GET`, `PUT` et `DELETE …/queues/{queueId}`. Lire demande post:read, et modifier post:update.

Ces requêtes placent des publications sur une file :

| Requête                                                                                                | Ce qu’elle fait                                                                                                                                                           |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `when: { "_tag": "queue", "queueId": "…" }` sur `send`, sur chaque élément de `bulk` et sur `validate` | Place une publication sur le prochain créneau libre de la file au lieu d’une heure. Sans `queueId`, sur la file par défaut de l’espace de travail.                        |
| `POST …/posts/{postId}/queue`, avec `{ "queueId"?, "channelIds"? }`                                    | Place un brouillon sur le prochain créneau libre, ou y déplace une publication programmée ou en attente d’approbation.                                                    |
| `GET …/queues/{queueId}/slots?count=…`                                                                 | Montre les prochains créneaux, chacun avec la publication qui le prend, et `nextFree`, où irait une publication ajoutée maintenant. C’est un conseil : rien n’est retenu. |
| `POST …/queues/{queueId}/reshuffle`                                                                    | Place les publications en attente de la file sur ses créneaux tels qu’ils sont maintenant ([plus bas](#reshuffle)).                                                       |
| `GET …/posts/search?queueId=…`                                                                         | Liste les publications qu’une file a placées. Chaque publication porte la file qui l’a placée (`queueId`, null une fois cette file supprimée).                            |

### Envoyer une publication sur une file [#queue-send]

Cette publication ne nomme aucun canal, et part donc sur les canaux de la file par défaut :

<CodeGroup>

```ts Node.js
import { PealClient } from "peal-sdk";

const peal = new PealClient({ token: process.env.PEAL_API_KEY });

const post = await peal.posts.send({
  channelIds: [],
  content: { text: "An evergreen tip.", media: [], overrides: [] },
  when: { _tag: "queue" },
});
```

```python Python

    when=PostTiming_Queue(),
)
```

</CodeGroup>

Peal choisit le créneau dans la transaction qui enregistre la publication, sous le verrou de la file. Des publications envoyées ensemble prennent donc des créneaux différents, et une requête renvoyée avec son `Idempotency-Key` n’en prend aucun.

Une publication qui ne nomme ni canal ni groupe de canaux va sur les canaux et le groupe de canaux de la file. Les `warnings` de sa réponse nomment les canaux de la file déconnectés depuis (`queueChannelsDropped`).

`validate` répond `queueSlot`, le créneau que la publication prendrait maintenant, c’est-à-dire l’heure sur laquelle tout le reste a été vérifié. Quand la file n’a plus de place, il répond `queueNoRoom`.

Les [outils MCP](/developers/mcp/tools#tools) nomment la file autrement : `when: { "_tag": "queue", "queue": "…" }`, par son identifiant ou son nom.

### Placer un brouillon sur une file [#queue-post]

`POST …/posts/{postId}/queue` place un brouillon sur le prochain créneau libre. Il va sur `channelIds` si vous les donnez, sinon sur ses propres canaux, sinon sur les canaux et le groupe de canaux de la file, avec les mêmes `warnings` qu’une publication envoyée sur la file.

Le créneau de la publication elle-même compte comme libre. Une publication ajoutée de nouveau à sa file reste donc où elle est, sauf si un créneau plus tôt s’est libéré depuis, qu’elle prend alors.

<CodeGroup>

```ts Node.js
const post = await peal.posts.enqueue({

  queueId: "0190f3a0-0000-7000-8000-00000000e001",
});
```

La requête peut être refusée avec ces erreurs :

| Statut | Code                 | Quand                                                                                                                      |
| ------ | -------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| 409    | `queue_has_no_room`  | La file n’a aucun créneau, ou tous ses créneaux des 366 prochains jours sont pris, avec `reason` `noSlots` ou `full`.      |
| 404    | `queue_not_found`    | La file n’est pas celle de l’espace de travail, ou l’espace de travail n’a pas de file par défaut.                         |
| 402    | `plan_limit_reached` | La place de l’abonnement se compte dans le mois du créneau. Quand ce mois est plein, Peal ne passe jamais au mois suivant. |

### Replacer les publications en attente [#reshuffle]

Enregistrer les créneaux d’une file ne déplace aucune publication. `POST …/queues/{queueId}/reshuffle`, sans corps, place les publications en attente de la file sur ses créneaux tels qu’ils sont maintenant ([Replacer les publications en attente](/guides/posts/queues#reshuffle)). Les publications en attente sont celles programmées ou en attente d’approbation, après maintenant, y compris celles déplacées à la main, et elles gardent l’ordre de leurs heures. Il faut post:schedule, ou post:create là où les publications attendent une approbation.

<CodeGroup>

```ts Node.js

});
```




```bash curl
  -H "Authorization: Bearer $PEAL_API_KEY"
```

```sh CLI
peal queues reshuffle "Weekdays"
```

</CodeGroup>

Chaque déplacement est un `reschedule` : l’abonnement est compté dans le nouveau mois, et `post.scheduled` est envoyé pour une publication programmée. Les approbations fonctionnent autrement :

- Une publication programmée passe par la règle d’approbation comme une publication de l’appelant.
- Une publication en attente d’approbation continue d’attendre à sa nouvelle heure, quel que soit l’appelant. Sa demande reste celle de la personne qui l’a faite, et `post.approval_requested` est envoyé avec la nouvelle heure.
- Une publication déjà sur son créneau n’est pas réécrite.

La réponse dit ce qui a été fait :

```json
{ "moved": 12, "unchanged": 3, "remaining": 0, "stoppedBy": null }
```

`remaining` compte les publications pas encore placées quand l’opération s’est arrêtée, et `stoppedBy` dit pourquoi :

- `planLimit` : un mois n’avait plus de place.
- `full` : il ne reste aucun créneau dans les 366 jours.
- `changed` : entre-temps, la file a été enregistrée, ou une publication y a été ajoutée sur un créneau pas encore atteint.

Rappelez-la pour continuer. Un second appel juste après le premier ne déplace rien. Une file sans créneau répond 409 `queue_has_no_room` (`noSlots`).

## Répéter une publication [#recycling]

`POST …/recycling` répète une publication programmée, en cours d’envoi ou en ligne ([comment ça marche](/guides/posts/queues#recycling)). Il répond 201 avec la règle, dont `coming` liste les trois prochaines publications et la variante de chacune.

Le corps prend ces champs :

| Champ      | Ce qu’il contient                                                                           |
| ---------- | ------------------------------------------------------------------------------------------- |
| `postId`   | La publication à répéter                                                                    |
| `every`    | `{ "count", "unit" }` : `unit` vaut `days` (1 à 365), `weeks` (1 à 52) ou `months` (1 à 12) |
| `count`    | Facultatif. Le nombre de publications en tout, la source comprise (2 à 100)                 |
| `until`    | Facultatif. Le dernier jour, en `YYYY-MM-DD` dans le fuseau de la source                    |
| `variants` | Facultatif. Chaque variante est `{ "text", "overrides"? }`, 10 au plus                      |
| `queueId`  | Facultatif                                                                                  |

Cette règle publie six fois en tout, toutes les deux semaines, avec une variante :

<CodeGroup>

```ts Node.js
const rule = await peal.recycling.create({

  count: 6,
  variants: [{ text: "Open all summer, as before." }],
});
```

### Gérer une règle [#recycling-manage]

Une fois la règle créée, ces requêtes la lisent et la modifient :

| Requête                                                    | Ce qu’elle fait                                                                                                                        |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| `GET …/recycling`                                          | Liste les règles, de la plus ancienne à la plus récente (`status`, `limit`, `cursor`)                                                  |
| `GET …/recycling/{ruleId}`                                 | En lit une                                                                                                                             |
| `PATCH …/recycling/{ruleId}`                               | Change son `count` ou son `until` (null le retire) ou ses `variants` (un tableau vide les retire), ou la met en pause (`paused`)       |
| `POST …/recycling/{ruleId}/resume`, avec `{ "variants"? }` | Relance une règle en pause, ou terminée pour `planLimit`, `contentRejected`, `noChannels`, `queueFull` ou `sourceWithdrawn` (plus bas) |
| `DELETE …/recycling/{ruleId}`                              | L’arrête. Les publications créées restent.                                                                                             |
| `GET …/posts/search?recyclingId=…`                         | Liste les publications créées par une règle. Chacune porte `recyclingId` et `occurrence` (sa place, la source étant 1).                |

Une règle se termine avec `sourceWithdrawn` quand sa publication a été annulée ou remise en brouillon. Vous pouvez la reprendre une fois la publication programmée de nouveau. D’ici là, la reprise répond 409 `post_not_recyclable`, et de même tant qu’une autre règle répète la publication. Au-delà de 100 règles en cours, elle répond 409 `too_many_recycling_rules`.

### Qui peut faire quoi [#recycling-permissions]

Les règles suivent ces permissions :

- Lancer, modifier, mettre en pause, reprendre et arrêter une règle demande post:schedule (ou post:create, pour la lancer, là où les publications attendent une approbation). Un membre du personnel agissant comme un membre ne le peut pas. La lire demande post:read.
- Changer, mettre en pause, reprendre ou arrêter une règle demande post:schedule, ou d’être la personne qui l’a lancée, agissant de la même façon : dans l’application web, par la même application ou avec la même clé.
- Chaque publication que crée la règle agit au nom de la personne qui l’a lancée, telle qu’elle est à ce moment-là. La règle d’une clé s’arrête une fois la clé révoquée.

Les requêtes peuvent être refusées avec ces erreurs :

| Statut | Code                         | Quand                                                                                                                                                                                                                                                          |
| ------ | ---------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 409    | `post_not_recyclable`        | La publication ne peut pas se répéter. `reason` : `draft`, `awaitingApproval`, `cancelled`, `repeating` (une autre règle la répète), `occurrence` (une règle l’a créée) ou `noChannels`.                                                                       |
| 422    | `recycling_variants_invalid` | Des variantes enfreignent les règles des canaux de la source, chacune par sa place à partir de 1 avec ses violations. Un texte de variante vide qui laisse sans texte un canal montrant des [médias propres](/developers/posting#channel-media) y est `empty`. |
| 422    | `recycling_ends_too_soon`    | La fin ne laisse aucune publication à créer.                                                                                                                                                                                                                   |
| 409    | `too_many_recycling_rules`   | 100 règles sont déjà en cours.                                                                                                                                                                                                                                 |
| 409    | `recycling_rule_ended`       | Une modification d’une règle terminée.                                                                                                                                                                                                                         |

La réponse est la règle. Elle contient ces champs :

- `approval` : `notNeeded`, `pending` ou `approved`.
- `channels` : ce que chaque canal peut porter, sorte par sorte. Chacun vaut `available`, `notAsked`, ou la raison pour laquelle il ne peut pas, comme `notAllowed` sur LinkedIn, ou `reconnect` sur un canal Bluesky connecté avant que Peal ne demande à y repartager.
- `followUps` : les dernières relances, chacune avec son `status` et sa `reason`.

Le `status` d’une relance vaut `armed` jusqu’à `until`, `waiting` jusqu’à `until` en attendant que son canal soit reconnecté, `sending`, `sent` (avec `platformPostId` et `permalink`), `failed`, `unconfirmed`, `expired` ou `cancelled`.

`FollowUpNotPossible` (422) refuse une règle qu’aucun canal ne peut porter, ou dont le commentaire est trop long pour un canal qui le pourrait, avec les mêmes `channels`. Sur une publication qui n’a plus rien à publier, il refuse aussi une règle qui n’armerait rien (`alreadyFollowedUp`, `windowPassed`).

Ces requêtes gèrent une règle :

| Requête                              | Ce qu’elle fait                                                                             |
| ------------------------------------ | ------------------------------------------------------------------------------------------- |
| `PATCH …/follow-ups/{ruleId}`        | Change `likes`, `comment` (null le retire) et `repost`, ou met la règle en pause (`paused`) |
| `POST …/follow-ups/{ruleId}/approve` | L’approuve. Un membre doit le faire en personne.                                            |
| `DELETE …/follow-ups/{ruleId}`       | L’arrête                                                                                    |
| `GET …/follow-ups?postId=…`          | Liste les règles d’une publication                                                          |

## Publier depuis un flux [#feeds]

`POST …/feeds` suit un flux web ([comment ça marche](/guides/posts/queues#feeds)). Peal le lit une fois, note comme vu chaque élément qu’il contient à ce moment-là, et n’en crée jamais de publication. Il répond 201 avec le flux et `seen`, le nombre d’éléments notés.

Le corps prend ces champs :

| Champ                        | Ce qu’il contient                                                                                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `url`                        | L’adresse du flux                                                                                                                                                                                                   |
| `channelIds`, `channelSetId` | Facultatifs                                                                                                                                                                                                         |
| `mode`                       | Facultatif. `draft` (par défaut) ou `queue` (sur `queueId`, ou la file par défaut de l’espace de travail)                                                                                                           |
| `queueId`                    | Facultatif                                                                                                                                                                                                          |
| `template`                   | Facultatif. Il accepte `{title}`, `{link}` et `{summary}`, 1000 caractères au plus.                                                                                                                                 |
| `attachPicture`              | Importe l’image de chaque élément dans la médiathèque pour sa publication (la personne qui ajoute le flux a besoin de media:upload). Le `pictureSkipped` d’un élément dit pourquoi une image a été laissée de côté. |

### Gérer un flux [#feeds-manage]

Ces requêtes lisent et modifient un flux :

| Requête                      | Ce qu’elle fait                                                                                                                                                                                                     |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET …/feeds`                | Liste les flux, du plus ancien au plus récent (`limit`, `cursor`)                                                                                                                                                   |
| `GET …/feeds/{feedId}`       | En lit un : son `status`, `lastCheckedAt`, `nextCheckAt`, `failingSince` et `lastFailure`                                                                                                                           |
| `PATCH …/feeds/{feedId}`     | Change ce qu’il nomme (une nouvelle `url` est lue aussitôt, comme à l’ajout), le met en pause (`"status": "paused"`) ou le relance (`"active"`, lu aussitôt, sans jamais créer de publication de ce qu’il contient) |
| `DELETE …/feeds/{feedId}`    | Cesse de le suivre. Ses brouillons et publications restent.                                                                                                                                                         |
| `GET …/feeds/{feedId}/items` | Liste ses 50 éléments les plus récents avec ce que chacun est devenu (`made`, `heldBack` avec sa `reason`, `skipped`, `claimed`, `abandoned`) et la publication créée, jamais leur texte                            |

Lire demande post:read. Tout le reste demande post:create, plus post:schedule pour un flux qui est ou devient `queue` : une application autorisée aux seuls brouillons ne peut donc pas en créer un. Sans post:schedule, vous ne pouvez modifier qu’un flux que vous avez ajouté, en agissant de la même façon.

Les requêtes peuvent être refusées avec ces erreurs :

| Statut | Code                    | Quand                                                                                                                                                                        |
| ------ | ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 422    | `feed_address_refused`  | L’adresse n’est pas une adresse HTTPS publique (`reason`).                                                                                                                   |
| 422    | `feed_unreadable`       | L’adresse n’est pas un flux (`notAFeed`, `tooLarge`, `unreachable`).                                                                                                         |
| 422    | `feed_template_invalid` | Le modèle nomme un autre champ.                                                                                                                                              |
| 409    | `too_many_feeds`        | L’espace de travail a déjà 10 flux.                                                                                                                                          |
| 429    | `feed_reads_limited`    | Ajouter, déplacer, reprendre et prévisualiser lisent 30 adresses par espace de travail et par heure. Au-delà, cette erreur arrive avec `retryAfterSeconds` et `Retry-After`. |
