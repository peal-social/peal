## Requêtes et réponses [#requests]

Les requêtes vont à l’adresse où vous ouvrez Peal, sous `/api`, et celles d’un espace de travail sous `/api/v1` ([L’espace de travail d’une requête](#workspace)). Les corps sont en JSON, envoyés avec `Content-Type: application/json`. Les réponses aussi, sauf celles qui n’ont pas de corps (204). Un corps d’un autre type répond 415 [`unsupported_content_type`](/developers/conventions/errors#error-codes).

Chaque réponse porte un en-tête `X-Request-Id`, quel que soit ce qui a répondu, et que la requête ait abouti ou non. Voici comment fonctionne cet identifiant :

- Envoyez votre propre `X-Request-Id` et Peal le garde, s’il compte de 8 à 128 caractères parmi les lettres, les chiffres, `.`, `_`, `:` et `-`. Sinon le serveur en attribue un, un UUIDv7.
- Cet identifiant figure sur chaque ligne que le serveur journalise pour la requête (`peal.request_id`), dans le corps de chaque erreur (`requestId`) et dans le [journal d’activité](/guides/workspace#activity) de l’espace de travail.
- Journalisez-le de votre côté, et citez-le quand vous demandez de l’aide.

Cette requête envoie son propre identifiant :

```bash
curl -i https://api.example.com/api/v1/channels \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "X-Request-Id: nightly-sync:2026-11-16:0042"
```

La réponse le garde :

```http
HTTP/1.1 200 OK
Content-Type: application/json
X-Request-Id: nightly-sync:2026-11-16:0042
RateLimit-Policy: "default";q=600;w=60
RateLimit: "default";r=599;t=42
Peal-Version: 2026-11-09
```

L’API ne fait qu’ajouter à ce qu’elle répond ([Versions](/developers/conventions/versioning#versioning)). Ignorez donc les champs, les valeurs et les erreurs que votre client ne connaît pas.

## Authentification [#authentication]

Chaque point d’accès de l’API demande un moyen d’authentification, envoyé en `Authorization: Bearer …`. Les exceptions sont les sondes de santé, le journal des modifications et les [documents de découverte](/developers/conventions/discovery#discovery). Quelques autres points d’accès répondent à quelqu’un qui n’est pas membre, par d’autres moyens :

- Les pages d’un [lien de connexion](/developers/embedding) ou d’un [lien de relecture](/guides/posts/review), qui répondent au jeton du lien.
- Les rappels de suppression de données des plateformes, que la plateforme signe.
- Ce que les pages de l’application web envoient avant toute connexion : ses rapports d’erreur, la clé de site du captcha, les routes de connexion sous `/api/auth`.

Deux moyens d’authentification appellent l’API :

| Moyen                   | Agit en tant que                                                        | Ce qui lui est permis                                                                                                                      |
| ----------------------- | ----------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Une clé d’API, `peal_…` | La clé elle-même, dans le seul espace de travail auquel elle appartient | Les permissions choisies à sa création, comme `post:read` ou `post:schedule` ([Clés d’API](/guides/workspace#api-keys))                    |
| Un jeton d’accès OAuth  | Le membre qui a connecté l’application                                  | Ce que le rôle du membre permet, dans la limite des scopes qu’il a accordés ([Ce que permet chaque permission](/developers/agents#scopes)) |

Le cookie de session de l’application web ne sert qu’à l’application web. Une requête dont le moyen d’authentification envoyé en `Authorization: Bearer …` est refusé reçoit une 401, quoi qu’elle porte d’autre. Peal ne se rabat jamais sur un cookie de session envoyé avec elle. La section [Authentification](/developers#authentication) de la présentation décrit chacun de ces moyens.

La référence de chaque point d’accès nomme la permission qu’il demande. Un jeton OAuth doit aussi porter le scope qui la contient :

| Scope               | Nécessaire pour                                                                                                                                                       |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `workspace:read`    | Lire                                                                                                                                                                  |
| `workspace:write`   | Changer quelque chose                                                                                                                                                 |
| `workspace:publish` | Tout ce qui demande `post:schedule`                                                                                                                                   |
| `workspace:ads`     | Ce qui atteint un réseau publicitaire : avec `workspace:write` pour `ads:manage`, avec `workspace:publish` pour `ads:spend` ([Publicités](/guides/engage/ads#access)) |

Chaque autorisation nomme la ressource à laquelle elle est destinée, l’API ou le point de terminaison MCP. Une autorisation sans ressource n’obtient aucun jeton (`invalid_target`) : Peal n’est pas un fournisseur d’identité pour d’autres applications.

Quand l’identifiant ne passe pas, vous recevez l’un de ces codes :

| Statut | Code                 | Quand                                                                                                                                               |
| ------ | -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400    | `workspace_required` | La requête ne nomme aucun espace de travail, et le moyen d’authentification n’appartient à aucun ([L’espace de travail d’une requête](#workspace)). |
| 401    | `unauthenticated`    | Aucun moyen d’authentification, ou un moyen qui ne fonctionne plus : une clé révoquée ou expirée, un jeton périmé.                                  |
| 403    | `forbidden`          | Le moyen fonctionne, mais ne permet pas la requête. `reason` dit pourquoi ([Erreurs](/developers/conventions/errors#forbidden)).                    |
| 404    | `not_found`          | Aucune ressource de ce nom, ou un espace de travail auquel l’appelant n’appartient pas.                                                             |

## L’espace de travail d’une requête [#workspace]

Les points d’accès d’un espace de travail sont sous `/api/v1`, et leurs chemins ne nomment pas l’espace de travail. Chaque requête agit dans un espace de travail, choisi dans cet ordre :

1. Celui dont l’en-tête `Peal-Workspace` donne l’identifiant, quand la requête l’envoie.
2. Sinon, celui auquel appartient le moyen d’authentification : celui d’une clé d’API, ou celui auquel est lié le jeton OAuth d’une application, comme celui d’un client MCP.
3. Sinon aucun, et l’API répond 400 `workspace_required` sans rien faire.

| Moyen d’authentification                    | Sans `Peal-Workspace`        | Avec `Peal-Workspace`                                                            |
| ------------------------------------------- | ---------------------------- | -------------------------------------------------------------------------------- |
| Une clé d’API                               | Son propre espace de travail | Son propre espace de travail. Un autre répond 403 `forbidden` (`wrongWorkspace`) |
| Une application liée à un espace de travail | Cet espace de travail        | Cet espace de travail. Un autre répond 403 `forbidden` (`wrongWorkspace`)        |
| La connexion de la ligne de commande        | 400 `workspace_required`     | Tout espace de travail auquel son utilisateur appartient                         |
| Une clé partenaire                          | 400 `workspace_required`     | Tout espace de travail que possède son compte partenaire                         |
| La session de l’application web             | 400 `workspace_required`     | Tout espace de travail auquel son utilisateur appartient                         |

L’en-tête est facultatif pour une clé d’API : son premier appel est donc `POST /api/v1/posts`, avec la clé et rien d’autre. Un espace de travail auquel l’appelant n’appartient pas répond 404 `workspace_not_found`, comme une valeur qui n’est pas un identifiant d’espace de travail. Un en-tête vide ne nomme aucun espace de travail, comme s’il n’était pas envoyé.

Une clé partenaire nomme l’espace de travail du client à chaque requête qu’elle y envoie :

```bash
curl https://api.example.com/api/v1/channels \
  -H "Authorization: Bearer $PEAL_PARTNER_KEY" \
  -H "Peal-Workspace: 7b1f6c1e-2d4a-4f0b-9c3e-5a8d2e6f1b90"
```

L’API partenaire garde l’identifiant d’un espace de travail dans le chemin quand l’espace de travail est ce sur quoi elle agit, comme dans `DELETE /api/v1/partner/workspaces/{workspaceId}` ([Intégrer Peal](/developers/embedding#workspaces)).
