## Versions [#versioning]

L’API n’a pas de version dans son chemin, et n’en a qu’une, parce qu’elle ne fait que grandir. Des champs, des opérations, des valeurs d’énumération et des erreurs s’ajoutent. Rien n’est renommé, retiré ni rendu plus strict.

Un client écrit aujourd’hui continue de fonctionner, tant qu’il ignore ce qu’il ne connaît pas :

| Ce que le client rencontre                                                                                                              | Ce qu’il fait                                                          |
| --------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Un champ qu’il ne lit pas, dans une réponse ou dans la charge utile d’un webhook                                                        | Il l’ignore.                                                           |
| Une valeur qu’il ne connaît pas, là où un champ énumère ses valeurs, comme un nouveau statut de publication ou un nouveau motif d’échec | Il la traite comme « autre chose », jamais comme un échec de décodage. |
| Un code d’erreur qu’il ne connaît pas                                                                                                   | Il se rabat sur le statut HTTP, et affiche `message`.                  |

<Callout
  type="info"
  title="Les tests bloquent tout changement qui pourrait casser un client"
>
  Chaque changement du contrat est comparé au dernier document OpenAPI publié,
  celui dont les SDK ont été générés (leur version 0.3.0 aujourd’hui). Les tests
  du projet échouent sur tout changement qui pourrait casser un client : une
  opération, un champ ou une valeur retirés ou renommés, un paramètre devenu
  obligatoire, ou un type qui a changé.
</Callout>

Une rupture ne se fait que sur décision. Elle est alors consignée avec sa raison et listée dans le [journal des modifications](#changelog) sous `breaking`. Quand un point d’accès disparaît, une [dépréciation](#deprecations) l’annonce d’abord.

Les charges utiles des webhooks suivent la même règle, avec leur propre `version` ([Versions](/developers/webhooks/requests#versions)).

## L’en-tête de version [#version-header]

Une version de l’API est le jour d’une publication du [journal des modifications](#changelog), comme `2026-11-09`. Chaque réponse porte la version que parle le serveur, sa dernière publication, dans un en-tête `Peal-Version` :

```http
HTTP/1.1 200 OK
Content-Type: application/json
Peal-Version: 2026-11-09
```

Envoyez dans le même en-tête la version pour laquelle votre client a été écrit. Les SDK et la ligne de commande envoient la leur à chaque requête : vous n’avez rien à régler. Le serveur répond de la même façon à tous les clients, quelle que soit la version envoyée, y compris absente ou inconnue, et compte les versions que ses clients envoient. Si une rupture est un jour décidée, ce décompte montre qui appelle encore avec une version plus ancienne.

## Dépréciations [#deprecations]

Un point d’accès déprécié continue de répondre comme il l’a toujours fait. Il le dit à trois endroits :

- Le document OpenAPI marque son opération `deprecated`, ce que montrent les clients générés et les éditeurs.
- Chacune de ses réponses porte les en-têtes ci-dessous.
- Le [journal des modifications](#changelog) le liste, par opération, dans la version qui l’a déprécié.

Voici ce que dit chaque en-tête :

| En-tête       | Ce qu’il dit                                                                                                                              |
| ------------- | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `Deprecation` | Depuis quand le point d’accès est déprécié, comme l’écrit la RFC 9745 : `@` suivi des secondes écoulées depuis 1970, comme `@1803859200`. |
| `Sunset`      | Quand il cessera de répondre, une fois que c’est décidé, sous forme de date HTTP (RFC 8594), comme `Wed, 01 Sep 2027 00:00:00 GMT`.       |
| `Link`        | Où la dépréciation est expliquée, avec ce qu’il faut appeler à la place, quand une telle page existe : `rel="deprecation"`.               |

`Sunset` et `Link` ne sont là que s’il y a quelque chose à dire : un point d’accès déprécié sans `Sunset` n’a donc pas de fin décidée. Faites journaliser par votre client toute réponse qui porte `Deprecation`.

Aucun point d’accès n’est déprécié aujourd’hui.

## Journal des modifications [#changelog]

`GET /api/changelog` liste les versions de l’API, la plus récente d’abord. Il ne demande pas d’authentification : un client peut donc le lire pour savoir ce que sait faire le serveur qu’il a trouvé.

<CodeGroup>

```ts Node.js
import { PealClient } from "peal-sdk";

const peal = new PealClient({ token: process.env.PEAL_API_KEY });

const changelog = await peal.system.changelog();
```


</CodeGroup>

La réponse liste une entrée par version :

```json
{
  "entries": [
    {
      "date": "2026-11-09",
      "title": "The API as the SDKs' release 0.3.0 calls it: 49 operations. Later entries list what each release adds to it.",
      "operations": [],
      "deprecations": [],
      "breaking": [],
      "additions": 0
    }
  ]
}
```

Chaque entrée a ces champs :

| Champ          | Ce qu’il contient                                                                                                                     |
| -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `date`         | Le jour de la version.                                                                                                                |
| `title`        | Ce qu’est la version, en une phrase.                                                                                                  |
| `operations`   | Les opérations qu’elle a ajoutées, par identifiant d’opération, comme `activity.list`.                                                |
| `deprecations` | Les opérations qu’elle a dépréciées, par identifiant d’opération.                                                                     |
| `breaking`     | Les changements qui pourraient casser un client, chacun avec le changement (`change`) et sa raison (`reason`). Presque toujours vide. |
| `additions`    | Le nombre total d’ajouts : opérations, champs, valeurs et erreurs.                                                                    |
