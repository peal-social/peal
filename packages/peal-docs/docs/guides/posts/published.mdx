Once a post is out, what you can still change depends on the platform. Some let Peal delete it or correct its text, and short links can tell you which channel brought visitors.

## Unpublish a post [#unpublish]

On a post's page, **Unpublish** deletes the post from that channel's platform, for everyone. Here's where Peal can delete posts, and where it can [edit them](#edit-live):

| Platform                | Unpublish | Edit | Why not                                                                                |
| ----------------------- | --------- | ---- | -------------------------------------------------------------------------------------- |
| Mastodon                | Yes       | Yes  |                                                                                        |
| Google Business Profile | Yes       | Yes  |                                                                                        |
| Discord                 | Yes       | Yes  |                                                                                        |
| Telegram                | Yes       | Yes  | Telegram deletes a message only within 48 hours of sending it                          |
| Slack                   | Yes       | Yes  | A Slack workspace can stop messages being edited after a while                         |
| Bluesky                 | Yes       | No   | Bluesky has no call to edit a post                                                     |
| X                       | Yes       | No   | X doesn't say which posts may be edited, or on which access                            |
| Pinterest               | Yes       | No   | Editing a Pin is in beta, not open to every app                                        |
| LinkedIn                | No        | No   | LinkedIn doesn't say which permission a deletion or an edit needs                      |
| Facebook Pages          | No        | No   | Meta says only some apps may delete Page posts, and not which permission an edit needs |
| Threads                 | No        | No   | Deleting needs a permission Meta grants after a review. Threads has no call to edit.   |
| Instagram               | No        | No   | Deleting needs a permission Meta grants after a review. Instagram has no call to edit. |
| YouTube                 | No        | No   | It needs a wider permission than the one Peal asks for                                 |
| TikTok                  | No        | No   | TikTok's API has no call to delete or edit a post                                      |

Where Peal can't, delete the post on the platform itself. Peal also can't unpublish in two cases:

- A post confirmed by hand, because Peal has no id for it.
- A post on a channel that's disconnected, turned off or needs reconnecting, until the channel is back.

<Callout type="warning" title="Unpublishing can't be undone">
  Neither Peal nor the platform can bring the post back, so Peal asks you to
  confirm first and names the channel. It deletes every part of a thread, the
  last first, so a deletion that stops midway leaves a shorter thread that still
  reads from its start.
</Callout>

Owners, admins and editors can unpublish, with the permission that publishes (`post:publish`). So can an API key that was given it, and an application allowed to publish. On the command line ([Posts](/developers/cli/posts#posts)):

```sh
peal posts unpublish <post-id> --channel <channel-id> --yes
```

### What happens next [#unpublish-progress]

The deletion runs in the background with the channel's other calls, one at a time. The channel shows **Removing…**, then **Removed from** the platform, with when.

The post stays **Published** in Peal, because it did go out, so the month's count and the usage don't change. Its address stays, struck through, as a record. A part the platform no longer has, because it was deleted there before, counts as deleted.

If the platform doesn't answer, Peal tries again after 1, 5, 15, 60 and 60 minutes. If it asks Peal to slow down, Peal tries again when it says. After that, the removal **failed**, with the reason, and **Try again** deletes what's left.

Statistics stop too. Analytics no longer reads the post and keeps the counts it already read. The inbox stops reading the post's comments and keeps the ones it has for their 30 days.

<Callout type="warning" title="A boosted post can't be unpublished">
  A post shown by a boost that isn't over can't be unpublished, because the ad
  would keep spending on a post that's gone. Stop the boost first.
</Callout>

## Edit a published post [#edit-live]

On Mastodon, Google Business Profile, Discord, Telegram and Slack, you can correct the text of a post that went out.

<Steps>
<Step title="Click Edit">

On the post's page, click **Edit** next to the channel. That channel's text opens, with the channel's counter.

</Step>
<Step title="Save">

Correct the text, then click **Save**. The new text replaces the old one on the platform.

</Step>
</Steps>

On the command line:

```sh
peal posts edit <post-id> --channel <channel-id> --text "Doors open at 7 pm, not 6."
```

Only the text changes. The media, the options, the audience and the time stay as they are.

<Callout type="warning" title="An edit is public at once">
  Whoever can unpublish can edit (`post:publish`), except a member whose posts
  need an [approval](/guides/posts/review). An approver makes the edit for them,
  because it would put out text nobody reviewed.
</Callout>

### What happens to the new text [#edit-live-progress]

The new text is checked the way a channel's text is when a post is scheduled: the platform's length (a Mastodon content warning counts), its characters, and the rest.

Once the platform takes it, it becomes that part's own text on that channel in Peal, and the other channels keep theirs. The channel shows **Edited on** with the date, and webhooks get `post.edited`. Peal keeps no earlier text, but Mastodon shows its own history of edits.

The edit runs in the background with the channel's other calls, and Peal tries it again the way it does a deletion. After that, it **failed**, with the reason, and **Try again** asks again.

<Accordion>
<AccordionItem title="Editing on Mastodon">

Peal sends Mastodon the post again with its media, its content warning and its sensitivity as they are on Mastodon at that moment, including changes made there since. That's because Mastodon clears whatever an edit leaves out. The post's language stays as it is.

A post with a poll is refused, because the edit would remove the poll.

Peal reads the post first, which needs the `read:statuses` permission. Channels connected before Peal asked for it don't have it, so reconnect the channel.

Each part of a thread is edited on its own, by its place counted from 0 (the post itself).

</AccordionItem>
</Accordion>

## Shorten links [#short-links]

On a server whose operator set where short links live (`PEAL_SHORT_LINK_BASE`), the composer shows **Shorten links** under the text. The box is ticked for new posts when the workspace's settings say so.

When a post asks for it, each link goes out replaced by a short address on each channel, if the link starts with `http://` or `https://` and is longer than a short address. The address redirects to the link and counts each visit.

Every channel, and every part of a thread, gets its own addresses, so you can tell which channel brought visitors. A send that's tried again uses the same addresses.

Peal never makes the text longer. A link is replaced only by an address that isn't longer than it, so the counters, the previews and the checks made when the post was scheduled all still hold. The text Peal keeps stays as you wrote it, and only what the platform receives changes.

A link without a scheme, a short one, or one that names a user and password is left as written. The line under the box says how many links will be shortened. Links also stay as written:

- on Pinterest, because its rules refuse link shorteners
- on Instagram and TikTok, whose captions make no link clickable
- for a link to a channel's own platform, because the platform shows it natively
- in an edit of a published post, which sends its text without short addresses

### The workspace's default [#short-links-default]

Owners and admins choose whether new posts ask for short links by default. In a workspace, click **Settings** at the foot of the sidebar, and on **Workspace**, under **Short links**, turn **Shorten links in new posts by default** on or off. The choice is saved at once. Whoever writes a post chooses for that post.

The default holds for every new post that doesn't say, wherever it's made: the composer, the API, an agent through MCP, the command line and feeds. A post takes the default when it's made and keeps it, so changing the default changes no post that already exists.

A post that says not to shorten its links never does. On a server without short links, nothing is shortened, whatever the default.

<Callout type="warning" title="Short links stop working with their workspace">
  If the workspace is deleted, or the operator changes or removes the short
  address, the short links in its published posts stop working.
</Callout>

[Analytics](/guides/engage/analytics#short-links) explains how clicks are counted.
