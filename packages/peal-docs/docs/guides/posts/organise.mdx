A workspace that posts every day repeats itself: the same channels, the same sign-off, the same campaign names. Peal keeps those for you:

- Tags file posts.
- Signatures end them.
- Channel sets start them.
- A channel's default options fill in what that channel always takes.

All of them belong to the workspace. Every member can read them, and those who can edit posts can change them.

## Who can do what [#roles]

Here's who can read and change them:

| Role        | Tags, signatures, channel sets and default options |
| ----------- | -------------------------------------------------- |
| Owner       | Read and change                                    |
| Admin       | Read and change                                    |
| Editor      | Read and change                                    |
| Contributor | Read and change                                    |
| Viewer      | Read                                               |

Changing them takes the right to edit posts. Through the API, that's `post:update`, and reading them is `post:read`.

## Tags [#tags]

A tag is a name and a colour, for a campaign, a client or a theme. A post has up to 10 tags, and a workspace keeps up to 100.

<Steps>
<Step title="Add a tag">

In a workspace, click **Settings** at the foot of the sidebar, then **Tags**, and add one there. Give it a name of 40 characters at most, which no other tag of the workspace has, whatever its case. Then choose its colour among the nine of the palette.

</Step>
<Step title="Tag a post">

In the composer, click **Tags** and tick the post's tags, or add a new one. To tag a post that went out, use its page. Tags mean nothing to the platforms, so you can change them whatever the post's status.

</Step>
</Steps>

To rename a tag, give it another colour or delete it, go to **Settings › Tags**. Deleting a tag takes it off its posts, which keep everything else.

### Filter the calendar by tag [#tag-filters]

Tags show on the calendar, as a dot of each tag's colour on the post, and in the list of drafts. Above the calendar, two filters narrow what you see:

- **Tags** shows only the posts filed under one of the tags you tick.
- **Channels** shows only the posts that go to one of the channels you tick.

With both, a post has to match both. The calendar says how many posts the filters hide, and **Clear filters** shows them all again.

## Signatures [#signatures]

A signature is a block of text a workspace ends its posts with, such as a sign-off, a disclosure or a set of hashtags. A workspace keeps up to 50, of 2,000 characters at most each.

To add one, click **Settings** at the foot of the sidebar, then **Signatures**. Give it a name and its text, and say what it's for: the whole workspace, one platform, or one channel. You can then use it in one of two ways.

### Add one while you write [#signature-insert]

In the composer, **Signature** lists the workspace's signatures. Choose one, and it goes under the text for all channels, or under one channel's own text, after a blank line.

### Make it a default [#signature-default]

Tick **Add to new posts by default**. A new post then shows **Add the default signature when the post is saved**, ticked. When you save the post, the workspace's default signature goes under its text, and the composer shows the text as saved. Untick the box for a post that should go without.

There's one default for the workspace, one per platform and one per channel. A platform's or a channel's own default replaces the workspace's there, so the post gets a text of its own on that channel, signed with it.

### How a signature behaves [#signature-rules]

Once added, a signature is part of the post's text like the rest:

- It counts against each platform's limit when the post is scheduled, so a post that fit without it may be refused with it.
- It's never added under a text that already ends with it. Saving twice, or adding it by hand to a post that has it, adds nothing.
- On a post in several parts (a [thread](/guides/posts#threads)), it goes under the last part, and the parts before it stay as they are.
- If you change or delete the signature later, the posts that hold it stay as they are.

Posts made through the API, MCP or the command line take a signature only when they ask for one. Nothing is added to a text unasked.

## Channel sets [#sets]

A channel set is a selection of the workspace's channels kept under a name, such as "Launch" or "Client A". It also keeps the [options](/guides/posts#options) posts take on some of them. A set holds up to 50 channels, and a workspace keeps up to 50 sets.

Here's how you work with sets:

- To save one, tick a post's channels, fill in their options, then click **Save selection as a set**.
- To use one, click **Use a channel set** when a post starts. It ticks the set's channels and fills in the options it keeps.
- To rename one, change its channels or delete it, go to **Settings › Channel sets**, which lists the sets.

### When a channel in a set is disconnected [#sets-disconnected]

A set keeps the channels it was given. When one of them is disconnected later:

- The set still lists it, marked as no longer connected.
- A post that uses the set goes to the set's other channels. Peal says which channel was left out, in the composer and in the API's answer (`warnings`), never silently.
- A post whose set has no connected channel left, and that names no other channel, is refused.
- Saving the set again takes the disconnected channel out of it.

## Default options for a channel [#defaults]

Some channels always take the same [options](/guides/posts#options), such as the same Pinterest board or the same YouTube audience. A channel's default options are what a new post takes on that channel when it gives none there.

Defaults may be unfinished. A post that takes them is checked when it's scheduled exactly like a post that wrote them itself, so they never get round a platform's rules.

Options are taken in this order: the post's own, then a channel set's, then the channel's defaults. Only a new post takes them, and a draft you change keeps what you give it.

You set them through the API, MCP or the command line:

```sh
peal channels defaults set 0190f3a0-0000-7000-8000-00000000c004 \
  --options '{"platform":"youtube","privacy":"unlisted"}'
```

## Duplicate a post [#duplicate]

On a post's page, or from its entry on the calendar, click **Duplicate**. You get a new draft that says what the post says: its text, its media, its channels with their own text and options, and its tags.

The copy has no time, and you're its author. Anything the workspace no longer has is left out, such as a channel disconnected since or media deleted since.

To send the same post at several times, duplicate it and schedule each copy.

## Through the API [#api]

Everything above is in the [HTTP API](/developers), under `/api/v1`, in the [MCP tools](/developers/mcp/tools#tools) and on the [command line](/developers/cli). These are the endpoints:

| What                    | Endpoints                                                                                                                             |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| Tags                    | `GET`, `POST …/posts/tags`, `PATCH`, `DELETE …/posts/tags/{tagId}`, `PUT …/posts/{postId}/tags`                                       |
| Signatures              | `GET`, `POST …/posts/signatures`, `PUT`, `DELETE …/posts/signatures/{signatureId}`                                                    |
| Channel sets            | `GET`, `POST …/channels/sets`, `PUT`, `DELETE …/channels/sets/{channelSetId}`                                                         |
| Queues                  | `GET`, `POST …/automations/queues`, `GET`, `PUT`, `DELETE …/automations/queues/{queueId}`, `GET …/automations/queues/{queueId}/slots` |
| Default options         | `GET`, `PUT`, `DELETE …/channels/{channelId}/default-options`                                                                         |
| Duplicate               | `POST …/posts/{postId}/duplicate`                                                                                                     |
| Posts filed under a tag | `GET …/posts?tagId=…`                                                                                                                 |

A post names what it takes when it's made. This one goes to the channels of the set "Launch", takes each channel's default signature, and is filed under a tag:

```sh
curl -X POST "https://peal.example/api/v1/posts" \
  -H "Authorization: Bearer $PEAL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "channelIds": [],
    "channelSets": ["Launch"],
    "content": { "text": "We are live.", "media": [], "overrides": [] },
    "defaultSignatures": true,
    "tagIds": ["0190f3a0-0000-7000-8000-00000000a001"],
    "when": { "_tag": "now" }
  }'
```

The fields work like this:

- `channelSets` names sets by id or by name, whatever the case, and `channelIds` may then be empty. The post goes to the sets' connected channels and to the channels it lists.
- `defaultSignatures` puts each channel's default signature under its text. `signatureId` puts one signature on every channel.
- `tagIds` files the post. Updating a draft without `tagIds` keeps its tags.

When a set lists a channel that's no longer connected, the post is made without it, and the answer says so:

```json
{
  "id": "0190f3a0-0000-7000-8000-00000000d010",
  "status": "scheduled",
  "warnings": [
    {
      "_tag": "channelsDropped",
      "channelSetId": "0190f3a0-0000-7000-8000-00000000b001",
      "channelSetName": "Launch",
      "channelIds": ["0190f3a0-0000-7000-8000-00000000c001"]
    }
  ]
}
```

`POST …/posts/validate` takes the same fields and answers the same `warnings`, so a script knows before it sends. In a [CSV import](/developers/posting/bulk#import), the `channels` column takes a set's id, or its name when the name has no space, comma or semicolon.

A [partner key](/developers/embedding) uses the sets, signatures and tags of each workspace its partner owns, as that workspace's own key does.
